# general-security: anonymous access and the password encryption policy

Manage the two general security settings the pinned JFrog provider exposes:
whether requests without credentials act as the anonymous user, and which
internal passwords HTTP Basic accepts. Use it to keep those platform-wide
settings in code next to the repositories and permissions they govern. It
creates no repositories or cloud resources.

## What it configures

- `artifactory_general_security.this`: anonymous access on or off, and the
  password encryption policy, `SUPPORTED`, `REQUIRED` or `UNSUPPORTED`.

## Prerequisites

- A running artifactweave or Artifactory with YAML descriptor PATCH and
  `GET /artifactory/api/securityconfig` available, and its base URL without
  `/artifactory`.
- An admin access token.
- Terraform 1.17 or later and `jfrog/artifactory` 12.11.14, as pinned in
  `versions.tf` and `.terraform.lock.hcl`.

## Inputs to set

```hcl
url                     = "https://artifacts.example.com"
enable_anonymous_access = false
encryption_policy       = "REQUIRED"
```

Pass the token through the sensitive `TF_VAR_access_token` environment
variable.

## Applying it

```sh
terraform init
terraform apply
terraform plan
```

The provider writes both settings through one descriptor PATCH and reads them
back from `/artifactory/api/securityconfig`, so the follow-up plan is empty.
The settings take effect on the next request; there is nothing to restart.

## Security

The access token is a sensitive input and stays out of ordinary plans and
logs. Anonymous access lets requests without credentials act as the anonymous
user, which can read only what its permissions allow; keep it off unless that
is intended. `REQUIRED` makes HTTP Basic refuse clear-text internal passwords
outside the web UI, including the administrator's, so clients must use the
encrypted password from `/artifactory/api/security/encryptedPassword` or an
access token. `UNSUPPORTED` refuses the encrypted password instead. Access
tokens are not passwords and are accepted under every policy, so keep one
before applying `REQUIRED`.

## Teardown

`terraform destroy` removes the resource from state only: the pinned provider
sends no request when it deletes it, so the settings stay as the last apply
left them. Apply `enable_anonymous_access = false` and
`encryption_policy = "SUPPORTED"`, the defaults, before destroying to return
the server to them.

## How this scenario is tested

The required Terraform conformance lane runs this reference against its own
temporary server through `test/terraform/run.sh`. The driver creates it at
the defaults, then changes one setting at a time: anonymous access on,
`REQUIRED`, anonymous access off, `UNSUPPORTED`, and back to `SUPPORTED`. At
each step it applies, refreshes and requires an empty plan, and
`test/terraform/check-general-security.py` reads the settings back and checks
their effect: a request without credentials is refused or served as the
anonymous user, and the bootstrap administrator's clear-text and encrypted
passwords log in over HTTP Basic or are refused as the policy says. After
`terraform destroy` it checks that the defaults remain in force and that the
state is empty.
