# identity: users, groups, a permission, a scoped token and a signing key pair

Users and groups, a permission over one repository, a token scoped to read that repository,
and a signing key pair, managed with the `jfrog/artifactory` and `jfrog/platform` providers.
It shows both identity APIs artifactweave serves: Access v2 (`platform_*`) and the legacy
security API (`artifactory_*`). See [Managing artifactweave with Terraform](../../README.md)
for the providers and how to authenticate them.

## What it configures

- `artifactory_local_generic_repository.team`: the repository `repository_key` the permission
  covers.
- `platform_group.developers`: the `developers_group` group, through Access v2.
- `artifactory_group.auditors`: the `auditors_group` group, through the legacy security API.
- `artifactory_user.developer`: `developer_user`, in both groups.
- `artifactory_managed_user.ci`: `ci_user`, in the developers group.
- `platform_permission.team`: `permission_name` over the repository. The developer user gets
  read, deploy and annotate; the developers group read and deploy; the auditors group read.
- `data.artifactory_permission_target.team`: the same permission read back through the
  legacy permission target API. `artifactory_permission_target` itself is a stub in provider
  12.x, so `platform_permission` writes it.
- `artifactory_scoped_token.ci`: a token for `ci_user` that can read the repository and
  nothing else, though its group could deploy there.
- `artifactory_keypair.signing`: the RSA key pair `keypair_name`.

## Prerequisites

- A running artifactweave (or Artifactory) and its base URL, without `/artifactory`.
- An admin access token: managing users and permissions needs `applied-permissions/admin`.
- Terraform 1.6 or later, which installs `jfrog/artifactory` 12.11.14 and `jfrog/platform`
  2.2.11 as pinned in `versions.tf` and `.terraform.lock.hcl`.
- An RSA key pair, with the private key in PKCS#1 form (`BEGIN RSA PRIVATE KEY`): the
  provider accepts no other. With OpenSSL 3:

  ```sh
  openssl genrsa -out signing.pem 2048
  openssl rsa -in signing.pem -traditional -out signing.pem
  openssl rsa -in signing.pem -pubout -out signing.pub
  ```

## Inputs to set

```hcl
url              = "https://artifacts.example.com"
repository_key   = "team-local"
developers_group = "developers"
auditors_group   = "auditors"
developer_user   = "developer"
ci_user          = "ci"
email_domain     = "example.com"
permission_name  = "team"
keypair_name     = "signing"
```

Pass the secrets through the environment rather than a file:

```sh
export TF_VAR_access_token=…
export TF_VAR_user_password=…   # must satisfy the server's password policy
export TF_VAR_keypair_private_key="$(cat signing.pem)"
export TF_VAR_keypair_public_key="$(cat signing.pub)"
```

## Applying it

```sh
terraform init
terraform apply
```

A second `terraform plan` shows no changes: both providers read back exactly what they
wrote.

## Security

- **Sensitive inputs.** The access token, the user password and the private key are
  sensitive variables, so Terraform keeps them out of plans and logs. All three are still
  stored in the state, so keep the state private.
- **The scoped token.** It is a credential, so this configuration doesn't output it. Read it
  from the state only where a job needs it.
- **What the permission allows:**
  - the developers group can deploy to the repository;
  - the auditors group can only read;
  - the CI user's token is narrower than its group, because a token's scope limits what its
    user's permissions allow.

## Teardown

`terraform destroy` revokes the token and removes the key pair, the permission, the users,
the groups and the repository with every file in it.

## How this scenario is tested

The gated `terraform` job runs `test/terraform/run.sh` against a fresh `-cover` artifactweave
(see [docs/testing/ci.md](../../../../docs/testing/ci.md#terraform-scenarios)).

- **Inputs passed:**
  - the fixture names `tf-team-local`, `tf-developers`, `tf-auditors`, `tf-developer`,
    `tf-ci`, `tf-team` and `tf-signing`;
  - the password `Terraform-user-1`;
  - a fresh PKCS#1 key pair for each run.
- **Steps:**
  1. It applies the configuration.
  2. It checks that the permission reads back through the legacy permission target API with
     its repository.
  3. It requires an empty plan.
  4. It destroys everything.
