# oidc: OIDC token exchange for CI workload identity

A GitHub Actions OIDC provider and a generic one, each with an identity mapping, managed with
the `jfrog/platform` provider. With these in place, a CI job exchanges its identity
provider's ID token for a short-lived artifactweave token and needs no stored secret
([decision 0005](../../../../docs/research/decisions/0005-authentication-and-tokens.md),
[research 21](../../../../docs/research/21-oidc-token-exchange.md)). See
[Managing artifactweave with Terraform](../../README.md) for the providers and how to
authenticate them.

## What it configures

- `platform_oidc_configuration.github`: GitHub Actions as an OIDC provider, accepting only
  tokens from `github_organization` with audience `audience`.
- `platform_oidc_configuration.ci`: any other OpenID Connect issuer at `ci_issuer_url`, such
  as GitLab or Jenkins.
- `platform_oidc_identity_mapping.main_builds`: builds of `main` in any repository of the
  organisation act as `ci_bot_user` for 10 minutes.
- `platform_oidc_identity_mapping.readers`: builds whose `project_path` matches
  `ci_project_path` get a token limited to `readers_group` for 5 minutes. With no username
  the token has a synthetic subject, so no auto-join group widens it.

## Prerequisites

- A running artifactweave (or Artifactory) and its base URL, without `/artifactory`.
- An admin access token.
- Terraform 1.6 or later, which installs `jfrog/platform` 2.2.11 as pinned in `versions.tf`
  and `.terraform.lock.hcl`.
- The user `ci_bot_user` and the group `readers_group`, with the permissions those builds
  need. The [identity](../identity/README.md) reference shows how to manage them.

## Inputs to set

```hcl
url                 = "https://artifacts.example.com"
github_organization = "my-org"
ci_project_path     = "my-group/**"
ci_issuer_url       = "https://gitlab.example.com"
audience            = "artifactweave"
ci_bot_user         = "ci-bot"
readers_group       = "readers"
```

Pass the token through the environment rather than a file: `export TF_VAR_access_token=…`.

## Applying it

```sh
terraform init
terraform apply
```

Nothing contacts the identity providers during the apply. Their signing keys are fetched
only when a CI job exchanges a token. A second `terraform plan` shows no changes.

A job then exchanges its token, for example `jf eot github <id-token> --url <artifactweave>`,
or `jfrog/setup-jfrog-cli` with `oidc-provider-name: github`.

## Security

- **What a token can do.** An exchanged token is only as wide as its mapping:
  - `main_builds` acts with everything `ci_bot_user` may do;
  - `readers` is limited to the group.
- **What to check when changing a mapping:** the claim it matches and the scope it grants.
  Broad claim patterns admit more jobs.
- **The access token** is a sensitive variable, but it is stored in the state, so keep the
  state private.

## Teardown

`terraform destroy` removes the two mappings and the two providers. Tokens already exchanged
stay valid until they expire, at most 10 minutes later.

## How this scenario is tested

The gated `terraform` job runs `test/terraform/run.sh` against a fresh `-cover` artifactweave
(see [docs/testing/ci.md](../../../../docs/testing/ci.md#terraform-scenarios)).
- **Inputs passed:** `github_organization = octo-org`, `ci_project_path = octo-org/**`, and
  the provider names `tf-github` and `tf-ci`.
- **What it checks:** it applies the configuration, requires an empty plan, and destroys
  everything.
- **Exchanging a token** is tested separately, in the `oidc` acceptance feature.
