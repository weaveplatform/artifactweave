# reverse-proxy: reverse proxy settings

Describe the web server in front of artifactweave with the pinned JFrog platform provider:
its type, the host name clients use, the ports it listens on and how Docker clients address
a repository. artifactweave stores the settings, serves them back and, for an NGINX server,
renders an nginx configuration snippet from them. Use it to keep the reverse proxy
description in code next to the server it fronts.

## What it configures

- `platform_reverse_proxy.this`: the single reverse proxy description of the instance, the
  `webServer` settings. Every write replaces it whole. The settings change no routing in
  artifactweave itself: `GET /artifactory/api/system/configuration/reverseProxy/nginx`
  renders them as an nginx snippet, and Docker subdomain requests are still matched by the
  server's `docker.subdomain_match` option.

## Prerequisites

- A running artifactweave or Artifactory with `GET` and `POST
  /artifactory/api/system/configuration/webServer`, and its base URL without `/artifactory`.
- An admin access token.
- Terraform 1.17 or later and `jfrog/platform` 2.2.11, as pinned in `versions.tf` and
  `.terraform.lock.hcl`.

## Inputs to set

```hcl
url                         = "https://artifacts.example.com"
server_provider             = "NGINX"
public_server_name          = "artifacts.example.com"
internal_hostname           = "localhost"
docker_reverse_proxy_method = "SUBDOMAIN"
use_https                   = true
ssl_certificate_path        = "/etc/ssl/certs/artifacts.crt"
ssl_key_path                = "/etc/ssl/private/artifacts.key"
```

Pass the token through the sensitive `TF_VAR_access_token` environment variable. NGINX and
APACHE need `public_server_name` and `internal_hostname`; HTTPS needs both paths. artifactweave
refuses `PORTPERREPO`, because it serves no port per repository.

## Applying it

```sh
terraform init
terraform apply
terraform plan
```

The follow-up plan is empty: the provider reads every field back from the `webServer` API.
For an NGINX server, `GET /artifactory/api/system/configuration/reverseProxy/nginx` then
returns the snippet to install in nginx's `http` context.

## Security

The access token is a sensitive input and stays out of ordinary plans and logs. The
certificate and key settings are paths on the web server host, never key material, and only
administrators read them back; other signed-in users see the method and ports only.

## Teardown

`terraform destroy` removes the resource from state only. The provider's delete sends no
request and warns "Reverse proxy cannot be deleted", so artifactweave keeps serving the last
settings; apply other settings to change them.

## How this scenario is tested

The required Terraform conformance lane runs this reference against its own temporary
server through `test/terraform/run.sh`. It applies revision 1, an HTTP-only NGINX server on
port 8080 with the repository path method, and revision 2, an APACHE server with HTTPS on
port 9443 and the subdomain method. After each it refreshes, requires an empty plan and runs
`test/terraform/check-p12.py`, which reads the settings back through the `webServer` API and
the XML descriptor's `reverseProxies` and asks for the effect: the nginx snippet listens on
the revision's port and proxies to its internal host, and is refused for APACHE. After
`terraform destroy` the checker requires the state to be empty and revision 2 to be served
unchanged. No host name or path in the fixture is contacted or read.
