# single-replication: push and pull configuration

This reference manages one local push target and one remote pull configuration
using `jfrog/artifactory` 12.11.14. The configuration runner qualifies administration
and credential lifecycle. The required `@replication_provider` acceptance matrix
also applies these resources to two isolated applications, executes push/pull,
checks destination/cache bytes and deletions, and destroys the managed resources
on both SQLite and PostgreSQL.

## What it configures

- A local generic source repository with `artifactory_local_repository_single_replication`.
- A remote generic cache with `artifactory_remote_repository_replication`, using
  the remote repository's canonical upstream URL.

The reference uses a pre-existing descriptor-managed proxy for push. It creates
no cloud resources. Choose a separate `repository_prefix` if these keys already
exist on your instance.

## Prerequisites

A running ArtifactWeave, a platform administrator access token, Terraform 1.17
or later and the pinned Artifactory provider. Supply a proxy key already present
in the instance configuration, plus absolute target/upstream repository URLs.

## Inputs to set

```hcl
url               = "https://artifacts.example.com"
repository_prefix = "managed-replication"
target_url        = "https://target.example.com/artifactory/destination"
upstream_url      = "https://upstream.example.com/artifactory/source"
proxy_key         = "existing-proxy"
revision          = 1
```

Pass `TF_VAR_access_token`, `TF_VAR_target_password` and
`TF_VAR_upstream_password` through the environment. Revision 2 changes
configuration fields and rotates the supplied credentials. The peer accounts are
`replicator-<revision>` for push and `replication-upstream-user-<revision>` for pull;
grant them access only to their corresponding peer repositories.

## Applying it

```sh
terraform init
terraform apply
terraform plan -detailed-exitcode
```

The follow-up plan must exit zero. Set `revision=2`, rotate the credentials, apply
and require another empty plan. Each configuration keeps its public target key
across the update. Event-driven and checksum options stay false; their true
forms remain unsupported rather than becoming configuration-only no-ops.

Revision 2 exercises the stored statistics flag by default. Set
`sync_statistics=false` and apply before executing ordinary P11 transfers;
statistics merging remains unsupported. The provider matrix verifies the explicit
501 refusal before applying this supported executing configuration.

## Security

API reads mask the target password and omit private worker revisions. Application
storage seals credentials. Terraform retains the sensitive push password in its
state; protect that state. The remote password uses the provider's write-only
attribute and an ephemeral input. Administration requires platform or current
project repository-management authority; this fixture uses platform authority.

## Teardown

`terraform destroy` deletes both configurations and their two repositories. A
proxy supplied by a user remains. The test runner removes its fixture proxy
through the strict descriptor PATCH after teardown.

## How this scenario is tested

The required provider lane applies revision 1 and requires an empty plan, checks
JSON representation, defaults/selected fields and credential redaction, rotates
secrets and applies revision 2, then repeats the checks and requires another
empty plan. It verifies stable target identity, sealed persistent bytes and no
unexpected target/upstream requests, destroys the resources and observes GET404
for both configurations. The proxy is seeded through descriptor PATCH because
provider proxy CRUD requires XML reads owned by P12. Fixture URLs point to unused
loopback paths; transfer behavior is outside this scenario.
