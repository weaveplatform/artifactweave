# 0034: npm local repositories

Status: Proposed

Checked against: **Artifactory 7.161.32** on 2026-10-17 ([research 25 section 11](../25-npm.md#11-artifactory-7x-check), [#341](https://github.com/weaveplatform/artifactweave/issues/341)); audited against KB, Jira and client sources on 2026-10-18 ([#378](https://github.com/weaveplatform/artifactweave/issues/378)).

## Context

npm, pnpm, Yarn and the JFrog CLI publish and install packages through the npm registry
protocol, which Artifactory serves at `/artifactory/api/npm/<repo>/`. Artifactory stores
each version as a tarball in the repository tree and keeps dist-tags as properties on the
tarballs, so the JFrog CLI can publish by an ordinary REST deploy and still be seen by
`npm install`. Decision [0032](0032-package-format-handlers.md) fixes how a format plugs
into the item service and the protocol router kit; this decision fixes what the npm
registry answers for a local repository and what it stores.
[Research 25](../25-npm.md) holds the facts, and its section numbers are cited below as R25.

## Decision

### Routes and names

- The registry is `/artifactory/api/npm/{repoKey}/`, mounted through the router kit of
  decision 0032 by `internal/server/npm`. The JFrog operations beside it (`POST .../reindex`,
  `GET .../auth/<scope>`) stay with the generated servers.
  - `api/npm/auth` and `{repoKey}/auth/{scope}` are the kit's reserved paths.
  - `{repoKey}/reindex` is not reserved: to any method but `POST` it names the package
    `reindex`, which exists on the public registry.
- A package name that begins with `@` takes two path segments, however its slash and `@`
  are percent-encoded: npm sends `@scope%2fname` (R25 1), and a slash that arrives
  unencoded is accepted too. Artifactory SaaS 7.164.0 fixed its own handling of the encoded
  slash (RTDEV-91009), which the self-managed notes up to 7.161.32 do not list, and 7.98.9
  accepts encoded slashes by default.
- After the name:
  - nothing is the packument;
  - `/<version or tag>` is one version manifest;
  - a path with a `-` segment is a tarball, served from the item at that path through
    `ServeItem`, so download counts and redirects apply;
  - `/-rev/<rev>` is an unpublish step, and so is a tarball's path followed by it.
- A first segment of `-` is one of npm's own operations. `/-/ping`, `/-/whoami`,
  `/-/v1/search`, the login and logout under `/-/user/`, and
  `/-/package/<name>/dist-tags`, with a tag after it to change one, have routes of their
  own; any other answers 404, as does any longer path under a package.

### Storage and properties

The canonical path of a tarball comes from the `package.json` inside it:
`<name>/-/<name>-<version>.tgz`, and for a scoped package
`@scope/name/-/@scope/name-<version>.tgz`. These are the paths npm names in its publish
body and the JFrog CLI deploys to (R25 2.1, 8). The version is `package.json`'s, cleaned as
npm's `semver.clean` cleans it: a leading `v` or `=` dropped, and build metadata too, which
npm ignores. It must be valid SemVer; otherwise the tarball is not indexed. The name must be
one npm accepts for an existing package (`validate-npm-package-name`'s
`validForOldPackages`).

**Reading the tarball.** On a `.tgz` whose path could be canonical, the npm format's
`Inspect` reads the tarball once, outside the write's transaction:
- `package.json` is the one directly inside the top-level folder, whatever that folder is
  called. npm strips that folder when it extracts, so a later entry of the same name replaces
  an earlier one, as it does here.
- `hasInstallScript` is true when `scripts` has a `preinstall`, `install` or `postinstall`
  script, or when the package has a `binding.gyp` and `gypfile` is not `false`, since npm
  then runs `node-gyp rebuild`.
- The read is bounded: a tarball of more than 2^20 entries, one that inflates past 16 GiB,
  or whose `package.json` is over 1 MiB is stored but not indexed.

If the tarball is at its canonical path, the hooks:
- link the package and the version in the package index (decision
  [0018](0018-package-index.md));
- set `npm.name`, `npm.version`, and, when `package.json` has them, `npm.description` and
  `npm.keywords`. Keywords are one value, a JSON array of strings (R25 5).
  - The stores cut every property value to 2400 UTF-16 code units, the limit JFrog
    documents (#338), so a long description is cut too. The keywords leave out those that do not fit,
    so `npm.keywords` stays a JSON array. The full text stays in the per-version document
    below.
  - A `package.json` without a description or keywords removes those properties.
- set `artifactory.licenses` to `package.json`'s `license` when it is a string, as 7.x
  writes it beside the `npm.*` properties (RTFACT-30834, R25 5).
  - It is one value, cut like any other.
  - A `package.json` without one leaves the property as it is. Other tools, Xray among
    them, write `artifactory.licenses` too, so removing it could lose what the format never
    wrote.
  - What 7.x writes for a legacy `license` object or `licenses` array, and whether it
    removes the property, are inferred [I].

These properties are set by the format and need no Annotate.

**An overwrite with other content** leaves the file none of its properties, as for every
package type (decision [0004](0004-storage-sql-metadata-and-blobs.md)): only those the
write brings are left, a deploy's matrix parameters or the properties a copy or move
carries over. The version's `npm.*` properties, its dist-tags and its deprecation
included, therefore go with the content they described. A file at the path that is no
longer that version's tarball, such as one overwritten with another version's content,
also drops the version from the index (under "Dist-tags and `latest`").

**Two more properties are the state npm changes after a publish:**
- `npm.disttag`, multi-valued, one value per tag (R25 5), `latest` among them, which is
  stored as any other tag is and moves by the rules under "Dist-tags and `latest`";
- `npm.deprecated`, the deprecation message. An empty message removes it.

Either may be changed through the npm protocol or the JFrog property API. The format's
`Annotated` hook (decision 0032) re-indexes the version on every change, by either route.
When a tarball gains a tag, the hook removes that tag from the package's other tarballs in
the same transaction, so a tag names one version.

**The per-version document** is `PackageVersion.Metadata` (`pkg/types/version.go`). It
caches:
- `package.json`;
- the `dist` facts: `shasum` from the stored SHA-1 and `integrity` from the stored SHA-512
  (decision 0032, #296);
- `hasInstallScript`;
- the version's tags and deprecation;
- its deploy time.

Packuments and search read the index and this cache, not the publish body. Nothing is
stored under `.npm/` (DV-042). Everything indexed follows from the tarballs and their
properties, so a reindex, a replica and a federation member reach the same packuments.

### Packuments

- **The full packument** (`application/json`) has the fields of 7.x's (RTFACT-30472,
  RTFACT-29708, R25 3):
  - `_id`, `_rev`, `name`, `description` (from `latest`, kept as `""` when it is empty, as
    7.x keeps it), `dist-tags`;
  - `versions`, each the cached `package.json` with `_id` (`<name>@<version>`), `dist`
    and `deprecated`;
  - `author` and `license`, copied from `latest`'s `package.json` as it has them, and left
    out when it has none;
  - `time`, with `"unpublished": null`, `created`, `modified` and one entry per version;
  - `"users": {}`.
- **The abbreviated packument** (`application/vnd.npm.install-v1+json`) has the fields
  npm's metadata document lists for it (R25 3): `name`, `modified`, `dist-tags`, and per
  version the dependency fields, `bin`, `engines`, `os`, `cpu`, `deprecated`,
  `hasInstallScript` and `dist`.
  - The dependency fields are `dependencies`, `optionalDependencies`, `devDependencies`,
    `peerDependencies`, `peerDependenciesMeta`, `acceptDependencies` and bundled
    dependencies under both spellings.
  - Each version also keeps `name`, `version`, `directories`, and `libc`, which npm checks
    with `os` and `cpu` before installing.
- **Which form:** the abbreviated one when it is the first type `Accept` lists, the full
  one otherwise. A `?write=true` read is always the full one. Each form answers with its own
  `Content-Type`, as Artifactory has since 7.90.5 (SaaS 7.89.2, RTDEV-43447).
- **`dist`** has `tarball`, `shasum` and `integrity`, as 7.x's has (RTFACT-30472), in both
  forms. npm's own registry adds `fileCount` and `unpackedSize`, which no JFrog client
  reads and npm does not need. The abbreviated form's `dist` on 7.x is inferred [I].
- **`dist.tarball`** is built on each request from the base URL (#315) as
  `<base>/artifactory/api/npm/<repo>/<canonical path>`, and is never stored.
- **`_rev`** is `"1-0"`, as in every 7.x capture (RTFACT-30472, RTFACT-29708; maintainer
  decision, 2026-10-18). Both captures are of packages with one version, so the `_rev` of a
  package with more is inferred [I].
- **`ETag` and `X-Checksum-Sha1`:** both forms carry the SHA-1 of the body sent, unquoted,
  in both headers, as 7.x sends them (RTFACT-30566). An `If-None-Match` that names it, with
  or without quotes or a weak prefix, or `*`, answers 304 with both headers and no body
  (RTFACT-19423).
  - The body is built for each request, from the versions its caller may read and the
    request's base URL, so its checksum changes whenever what it shows does.
  - Both captures are of remote or virtual repositories. That a local repository sends
    them, and what 7.x's checksum is taken over, are inferred [I].
  - A version manifest carries neither.
- **`time`:** `created` is the package's first indexing in the repository, which a reindex
  keeps; `modified` and each version's entry are when its tarball was last deployed.
- **`deprecated`** is a string, the `npm.deprecated` message, as the public registry gives
  it and as a 7.x local repository shows it (RTFACT-30928, RTFACT-14726, R25 5). A
  `deprecated` field in the author's `package.json` is replaced by it, or dropped when the
  property is absent.
- **Readable versions only:** a version whose tarball the caller cannot read is left out,
  with the tags that name it, and `latest` is resolved among the versions left.
  - A caller that cannot read the package's folder is refused, 401 or 403 as the item
    routes refuse, whether or not the package exists.
  - A caller that can read the folder, but finds no version it may read, gets 404.
  - A version manifest is held to the same rules, so a hidden version is a 404.

### Publishing

`PUT /<name>` whose body has `_attachments` is a publish (R25 2.1):
- **Streaming:** the body is read as a stream. The attachment's base64 is decoded straight
  into the blob store, whatever order the body's fields come in. The request may be at
  most `npm.max_publish_size` (default `1GiB`); a larger one answers 413. The fields outside
  the attachments' data are held in memory, and may total at most 64 MiB; more answers 413
  too, so a body within the cap cannot make the server hold a gigabyte of description.
- **Permission first:** a caller who may deploy nothing in the package's folder is refused
  before the body is read. Deploy on the canonical path itself is checked once the body has
  named the version.
- **Shape:** the body must name exactly one version, and the name in the URL, `name` and,
  when sent, `_id` must agree. Exactly one attachment's name must end in `.tgz`; other
  attachments, such as a provenance bundle, are read past and not stored.
- **Validation:** the tarball's `package.json` must give the body's name and version, and
  `length`, when sent, must equal the decoded size. Any failure answers 400. The tarball is
  in the blob store by then, since it may arrive before the fields that name it; a refused
  tarball is collected as an orphan.
- **Checksum policy:** `dist.shasum` and each `dist.integrity` hash of an algorithm the
  server computes (SHA-512, SHA-256, SHA-1) are the client's checksums, and the repository's
  checksum policy applies to them, as 7.x applies it from 7.31.10 (RTFACT-14280, R25 2.1).
  - Under `client-checksums` each must match the tarball, or the publish answers 400. 7.x's
    status for that refusal is inferred [I].
  - Under `server-generated-checksums` none is checked.
  - Either way each is recorded as the tarball's original checksum, so a mismatch shows in
    the bad-checksum search as a REST deploy's does. `dist.shasum` outranks an integrity
    `sha1`, and a value too malformed to be a checksum of its algorithm is not recorded.
- **Release and snapshot handling:** `handleReleases` and `handleSnapshots` apply to every
  write of a file whose path has the shape of a canonical path, a publish, a REST deploy, a
  copy and a move alike. One the repository does not handle answers 409 with "The
  repository '<repo>' rejected the resolution of an artifact '<repo>:<path>' due to
  conflict in the snapshot release handling policy." (KB 000006800, R25 2.1). The KB elides
  the message's opening, which is 6.20's, as for Maven [I].
  - The version is read from the path: a pre-release is a snapshot and any other version a
    release. This is inferred [I]: no 7.x source says how it classes npm versions, and the
    `npm-default` layout 7.x exports does not settle it, since its greedy `[module]` reads
    a pre-release's last hyphen as the one between module and base revision and finds no
    integration revision (research 03).
  - A path that names no version this way is not checked, as Artifactory leaves alone a
    path its layout cannot read.
  - The handling is checked after a blacked-out repository and before the include and
    exclude patterns, in Artifactory's order. A checksum upload is exempt.
- **Republish:** a version that already exists, or whose canonical path holds an item,
  answers 403 for every caller, administrators included, as Artifactory does (R25 2.1).
  The path is checked inside the write's transaction. npm 11 and later refuse such a
  publish before sending it unless `--force` is given.
- **Tags:** the body's dist-tags other than `latest` are stored as `npm.disttag` on the new
  tarball, which moves them from older versions. The body's `latest` is ignored, as 7.x
  ignores it (RTFACT-8184, RTFACT-26099): the format gives `latest` by its own rules (below).
  The tags a publish sets need Deploy, not Annotate.
- **Success** answers 201, as 7.x does (RTFACT-24072, KB 000004147, R25 2.1), with
  `{"ok":true}`. npm ignores the body, and 7.x's is inferred [I].
- **Other routes:** a REST deploy of a tarball (`jf npm publish`, `jf rt u`) is an ordinary
  item deploy. Overwriting needs Delete, as for any item, and the hooks re-index the new
  content. `POST /-/stage/package/...` (`npm publish --stage`) is not served.

### Dist-tags and `latest`

- **The operations** (R25 2.2):
  - `GET /-/package/<name>/dist-tags` answers `{tag: version}`.
  - `PUT /-/package/<name>/dist-tags/<tag>`, with a JSON-string version, sets
    `npm.disttag=<tag>` on that version's tarball and removes the tag from the others.
  - `DELETE /-/package/<name>/dist-tags/<tag>` removes the tag.
- **Statuses:**
  - each operation answers 200 with the resulting `{tag: version}` map, as the caller sees
    it;
  - an unknown package, version or tag answers 404;
  - a tag that is a valid SemVer range answers 400, matching the check the client makes
    before sending (R25 2.2);
  - a `PUT` of the whole map, `/-/package/<name>/dist-tags`, which npm never sends, answers
    405.
- **Permission:** a change needs Annotate on the package's folder before the body is read,
  then on each tarball that gains or loses the tag; a refusal changes nothing.
- **`latest`** is stored as 7.x stores it, as `npm.disttag=latest` on one tarball (7.84.10,
  RTDEV-40221; RTFACT-31340, RTFACT-21400, R25 7). It moves only by these rules:
  1. `npm dist-tag add <version> latest`, or `npm.disttag=latest` set on a tarball by any
     route (the property API, a deploy's matrix parameter, a copy, move or restore carrying
     it) makes that version `latest` (RTFACT-16009, RTFACT-7400).
  2. A new version written without a dist-tag takes `latest` when it outranks the version
     that has it. By default a version that is not a pre-release outranks every
     pre-release, and between two of the same kind the higher SemVer wins;
     `npm.tag_latest_by_publish` (below) ranks them by deploy time instead. The default is
     the stable-first rule Jira RTFACT-30783 and RTFACT-17732 show in a local repository;
     KB 000007043 records it for the `latest` that virtual repositories merge from
     7.120.0 (R25 7).
  3. A new version written with a dist-tag (`npm publish --tag`, `;npm.disttag=` on a
     deploy) leaves `latest` where it is, unless the package has none yet (RTFACT-24072,
     RTFACT-14111, R25 7).
  4. A package left without `latest`, its version removed (unpublish, delete, move out, an
     overwrite with another version's content) or the tag taken off (`npm dist-tag rm`, the
     property API), gives it to the version that outranks the others by rule 2's order.
     `npm dist-tag rm latest` can therefore hand `latest` back to the version it was taken
     from.

  A redeploy of a version with the same content moves nothing, so it never undoes an
  `npm dist-tag add`. A reindex keeps `latest` where the properties have it, and settles
  it by rule 4 for a package whose tarballs carry none, writing the property.
- **An overwrite with other content** leaves the tarball none of its properties (under
  "Storage and properties"), so its dist-tags and deprecation go, and `latest`, if it was
  among them, moves by rule 4, as for any removal (#515, #518). This applies to a REST
  deploy, a copy and a move onto the path; a publish never overwrites (the republish 403).
  - A rebuild of the same version is other content too: its tags go, and rule 4 gives
    `latest` back to it only when it outranks the others.
  - An overwrite with another version's content also drops the version. Without the
    clearing, the file would keep tags that name no version, and the strict-layout
    conversion, which moves the file to its own canonical path, would give them to its
    version, `latest` included (rule 1), and show it deprecated although nobody deprecated
    it.
  - A write that sets `npm.disttag` itself, by a deploy's matrix parameters or the
    properties a copy or move carries over, brings its own tags, which stay. A restore
    sets the properties it recorded, so they stay too.
  - What 7.x does with the tags and deprecation of an overwritten tarball is inferred [I]
    from 6.20, whose overwrite clears every property (decision
    [0004](0004-storage-sql-metadata-and-blobs.md)).
- **Reads** serve the stored tag. When the caller cannot read the version that carries it,
  or no version does, the read resolves `latest` by rule 4 among the versions the caller
  can read, and writes nothing.
- **`npm.tag_latest_by_publish`** (default off) is the equivalent of 7.x's global
  `artifactory.npm.tag.tagLatestByPublish`, which is off by default too (6.20's
  `ConstantValues`; RTFACT-20127, R25 7). It ranks versions by when their tarballs were
  last deployed, the later first, in rules 2 and 4:
  - A new version written without a dist-tag takes `latest`, "the most recently uploaded
    package" (npm-repositories), a pre-release included (RTFACT-20127).
  - A new version written with a dist-tag still leaves it (rule 3): RTFACT-9754, which
    added the setting, tags a publish `latest` "if no tag was specified".
  - A removal, or `latest` taken off, gives it to the version deployed last, and so do a
    reindex and a read that cannot see `latest`'s version.
  - A redeploy of a version with the same content still moves nothing, though its deploy
    time moves on. A copy or a move keeps a version's deploy time, so a version moved in
    takes `latest` only from one deployed before it. Two versions deployed at one moment
    are ranked by the default order. These three are inferred [I].
  - The setting reaches every write through the npm format's handler, which carries the
    formats' settings (`formats.Settings`), as `npm.enforce_path` does, and the registry's
    reads through the protocol's options. See "Format settings" under Rationale.
- **Why a publish's `latest` is ignored:** every npm publish names `latest` unless `--tag`
  is given, so storing it would make every published version `latest`, and rule 2 could
  never apply.

### Deprecation and unpublish

- **Packument updates:** `PUT /<name>` without `_attachments` is a packument update, as
  `npm deprecate` sends it (R25 2.2).
  - Only each version's `deprecated` is applied: the format sets, changes or removes
    `npm.deprecated` on that version's tarball. A message that is empty, or no string,
    removes it.
  - Versions missing from the body, or that the index lacks, are left alone, and other
    fields are ignored.
  - Only the body tells a packument update from a publish, so Deploy or Annotate on the
    package's folder lets the body be read. The update then needs Annotate on each tarball
    that changes, checked for all of them before any changes.
  - It answers 200 `{"ok":true}`; an unknown package answers 404, and `versions` that is
    not an object, or a version that is not one, 400.
- **Unpublish** follows npm's flows (R25 2.2):
  - `PUT /<name>/-rev/<rev>` removes each version the caller can read that the body leaves
    out. A version the caller cannot see is never removed for being absent from its body,
    and a body without `versions` answers 400 rather than removing everything.
  - `DELETE /<name>/-rev/<rev>` removes every version, those the caller cannot read
    included, so it needs Delete on each.
  - `DELETE /<tarball path>/-rev/<rev>` removes that tarball. npm sends it after the `PUT`
    that already removed its version, and takes the 404 it gets as done.
  - Each removal goes through the trash can and needs Delete on the tarball, checked for
    every tarball before any goes. Tags on a removed version go with it, and `latest`
    moves by rule 4.
  - Dist-tags and other fields in the `PUT` body are ignored: the client computes `latest`
    with prereleases included, and the server's rules apply instead.
  - Each answers 200 `{"ok":true}`, a package or tarball already gone 404, and a `DELETE`
    without `-rev/<rev>` 405.
  - Only the versions' tarballs are removed. Whether 7.x also removes the package's
    folder, and files in it off their canonical paths, is inferred [I].
- **`_rev`:** every packument's `_rev` is `1-0` (above), so the `<rev>` of a `/-rev/`
  request cannot show that the client's view is stale, and it is compared with nothing
  (maintainer decision, 2026-10-18). A packument update carries no `_rev`.

### Search, ping and whoami

- **`GET /-/v1/search?text=&size=&from=`** reads the package index and the per-version
  cache:
  - The first three whitespace-separated terms of `text` must each appear, ignoring case,
    in the name, the description or a keyword of the package's `latest` among the versions
    the caller may read. Three is the number 7.x documents (7.125.4, R25 3). A fourth term
    is not read, and an empty `text` matches every package [I].
  - `size` defaults to 20, npm's own `searchlimit`, and has no cap: JFrog's KB on npm
    search has users raise `--searchlimit` to 1000 to see past the first 20 (R25 3). `from`
    defaults to 0. A value that is no number, or not positive, takes its default [I].
    Results are ordered by name. `quality`, `popularity` and `maintenance` are ignored.
  - The body is 7.x's (RTFACT-26660, R25 3),
    `{"objects":[{"package":{"name","description","maintainers","version","date","keywords","author"}}]}`,
    with no `score`, `searchScore`, `total` or `time`. npm 12 needs none of them: it reads
    each object's `package`, and its output reads `maintainers` as a list (R25 3).
    - `description`, `keywords` and `author` are the latest version's, as its
      `package.json` has them; one it lacks is `null`, or `[]` for keywords, as
      RTFACT-26660 shows them.
    - `maintainers` is always `[]`: nothing here records who publishes a package.
    - `date` is when the latest version was deployed. RTFACT-26660's capture has `null` for
      every package, so whether 7.x fills it is inferred [I].
  - Packages the caller may read no version of are left out; nothing is refused.
  - A publish is searchable once it commits: the deploy keeps the index current in its
    own transaction, so no work queue is involved (decision 0032). Artifactory calculates
    its search index asynchronously (R25 3); the difference is DV-071.
- **`GET /-/ping`** answers 200 `{}` to any authenticated caller, and to anonymous callers
  when anonymous access is on (R25 3).
- **`GET /-/whoami`** answers `{"username":"<name>"}`, or 401 to an anonymous caller. npm
  calls it only when it holds a token (R25 3).

### Login and tokens

The middleware reads no credentials on `/-/user/` paths, and lets a request without any
through while anonymous access is off; Artifactory lets anonymous requests reach the same
paths (R25 4). npm sends a login with whatever token `.npmrc` holds, which a stale one would
otherwise refuse, and a logout with the token it ends, which may have expired (R25 4). Both
routes check the password or the token they carry themselves and act as no caller, and a
stale password sent with them is not counted as a failed login.

- **Legacy login,** `PUT /-/user/org.couchdb.user:<user>`:
  - checks `password` exactly as a Basic login checks a password (decision
    [0005](0005-authentication-and-tokens.md)): the basic authentication switch, the user
    lock, the temporary login suspension, the password expiry, a disabled user and a
    disabled internal password all apply, with the same answers, and a wrong password
    counts toward the lock and the suspension;
  - the body's `name` must be the user the URL names (400 otherwise), and the body may be
    at most 64 KiB (413);
  - `token.allow_basic_auth` does not apply. It governs the Access token API alone, and
    the legacy `POST /api/security/token`, which also exchanges a password for a token,
    takes one whatever it says (decision 0005). JFrog's npm page logs in with `npm login`,
    and JFrog's 7.x request log shows a login answering 201 (KB 000004147); that 7.x does
    not hold npm login to "Enable Token Generation via API" is inferred [I];
  - a token sent as the password logs in only as the stored user it acts as, as a Basic
    password that is a token does. A token narrowed to groups or resources, a registry
    token or a transient user's answers 401: it would otherwise obtain a broader
    credential;
  - on success answers 201 `{"ok":true,"id":"org.couchdb.user:<user>","token":"<token>"}`;
  - the token is an access token of decision 0005 with the user's own permissions,
    described `npm login`, and always revocable, so a logout ends it whatever its lifetime;
  - the token expires after `npm.login_token_expiry` (default `720h`, the month 7.x gives
    it, KB 000006713), as an hourly `npm login` would be unusable;
  - a refused password answers 401 for a wrong password or an unknown user, and 403 for a
    locked account, a suspended name or an expired password, never 400 or 409. npm reports
    a 400 as "no such user",
    which would reveal which names exist, and it reads a 409 as "update the user", which
    is not served. A transient user cannot log in (R25 4).
- **Web login:** `POST /-/v1/login` answers 405 in the npm envelope until #262, since no
  route takes `POST`, or 401 to a request without credentials while anonymous access is
  off. npm falls back to legacy login on either (R25 4).
- **Logout,** `DELETE /-/user/token/<token>`:
  - revokes the token whose access or reference token the path names, since holding it
    proves the right to end it, so the token npm logged in with stops authenticating at
    once;
  - answers 200 `{"ok":true}` in every case, because npm keeps the stale token in `.npmrc`
    unless logout succeeds (R25 4). A token already gone is left as it is, and so is one
    that cannot be revoked: shorter than the revocable threshold and neither forced
    revocable nor refreshable, which a login's never is;
  - the access log records its path with the token replaced by `[redacted]`.
- **`GET /artifactory/api/npm/auth`** answers `text/plain` `.npmrc` lines. An anonymous
  caller gets 401. No `always-auth` or `email` line is sent: 7.x stopped sending both in
  7.161.26 (R25 4).
  - A caller that sent its password with Basic gets `_auth = <base64 of
    user:<encrypted password>>`, as JFrog's 7.x documentation shows it (R25 4). The
    encrypted password is the reference token `GET /api/security/encryptedPassword`
    returns (DV-004), so the password itself is never written back.
  - A caller that sent a token gets that same token back: as `_auth` beside the user name
    it sent, when it sent the token as a Basic password, and otherwise as
    `_authToken = <the token>`. It is a credential the caller holds already, so nothing new
    is handed out. 7.x answers an access token (RTFACT-30181); its body is inferred [I].
- **`GET /artifactory/api/npm/<repo>/auth/<scope>`** answers `@<scope>:registry=<registry
  URL>`, then the credential keyed to that registry URL without its scheme, as JFrog's 7.x
  documentation shows it (R25 4): `_password=<base64 of the encrypted password>` and
  `username=<user>` for a Basic caller, or `_authToken=<the token>` for a token caller.
  - The scope comes without its `@` (R25 4); one sent with it is read without it [I]. A
    scope npm would not accept answers 400, since it is written into `.npmrc` [I].
  - Any npm repository may be named, whatever its class. Another package type answers 400
    and a missing repository 404 [I].
  - It is in the OpenAPI sources as `x-unverified`.
- **Both operations** answer errors in the Artifactory envelope,
  `{"errors":[{"status","message"}]}`, as 7.x does (RTFACT-30181, R25 4), and so does the
  405 the router kit answers another method on them.
- **Not served:** `/-/npm/v1/tokens` and `/-/npm/v1/user`, which npm calls for `npm token`
  and `npm profile`, answer 404 until P19 finds whether Artifactory serves them (R25 4).

### Strict layout, conversion and reindex

- **Strict layout:** every npm local repository behaves as one with "Enforce strict
  layout" on, which is Artifactory's default for a new repository (R25 6). There is no
  switch (DV-041).
  - A `.tgz` at a path other than its canonical one, or one without a readable
    `package.json`, is stored but not indexed. It can still be downloaded at its path.
- **Enforce path:** `npm.enforce_path: true` (default `false`) is the equivalent of 7.x's
  global `artifactory.npm.enforce.path`, which prevents, on every npm local repository,
  "uploading packages with file names that do not match the internal metadata of the
  package" (npm-repositories, "Use npm Enforce Path Layout"; 7.146.22 fixed uploads that
  slipped past it, RTDEV-86877; R25 6). It applies only to uploads made while it is on, and
  files stored before stay.
  - An upload of a `.tgz` whose `package.json` is readable must be named
    `<name>-<version>.tgz`, with the version cleaned as the index cleans it and a scoped
    name's scope kept, as npm names its tarball: `@scope/name/-/@scope/name-1.0.0.tgz`
    passes and `@scope/name/-/name-1.0.0.tgz` does not. Any other answers 400 with
    `The repository '<repo>' rejected '<path>': the file name of npm package
    <name>@<version> must be <file name>.`
  - The uploads are a REST deploy, a checksum deploy, an archive's entry and npm publish,
    in a local or federated repository. A publish always meets the rule, since it stores
    the tarball under the name its own `package.json` gives.
  - Inferred [I], none of it documented: the status and message; that the folders before
    the file name are not compared, so a tarball named rightly but off its canonical path
    is stored but not indexed, as strict layout stores it; that the scope is compared;
    that content without a readable `package.json`, and a file not named `.tgz`, are
    stored; that a federated repository is checked; and that a copy or move, which is no
    upload, is not.
- **Conversion:**
  - `POST /api/v1/migrations/npm/repositories/<repo>/migrate` queues a conversion on the
    work queue (decision [0033](0033-persistent-work-queue.md)), keyed by repository, and
    answers 202 with no body. Asking again while one is pending joins it.
  - The conversion moves each tarball that is not indexed, but whose `package.json` gives
    a canonical path, to that path, as a REST move would, so the hooks index it there. The
    run is idempotent.
  - A tarball without a readable `package.json` stays where it is, and so does one whose
    canonical path already holds the same content, which needs no move.
  - A canonical path that holds anything else, or a move the repository refuses (its
    release and snapshot handling, say), is skipped and reported: the conversion moves
    every other tarball, then fails naming each one it skipped, at most ten. The work
    queue retries it and, once its retries run out, parks it, logging the failure each
    time. What 7.x does with a canonical path already taken is inferred [I].
  - `.../resume` queues again a conversion the work queue parked, with a fresh set of
    attempts, and answers 202; with none parked it answers 400.
  - The response bodies are inferred (R25 6).
- **Reindex:** `POST /api/npm/<repo>/reindex` queues the format's rebuild of the index on
  the work queue, keyed by repository, and answers 200 in plain text with 7.x's words,
  `Recalculating index for npm repository <repo> scheduled to run` (JFrog's archived REST
  reference; KB 000005641). The rebuild makes the index and the per-version cache from
  the tarballs and their properties, `latest` included (rule 4 above).
- **Which repositories:** all three operations need Manage on the repository, as 7.x
  requires from 4.8 ("only requires the set of permissions assumed by Manage", JFrog's
  archived REST reference), and act on npm local repositories only. A missing repository
  answers 404, a caller without Manage 401 or 403, and any other repository 400; the order
  of those checks is inferred [I].
- **Errors:** the three operations answer in the Artifactory envelope,
  `{"errors":[{"status":…,"message":…}]}`, as 7.x's JFrog operations beside the registry do
  (RTFACT-30181). A `GET` of `.../reindex` is the package `reindex`, so its answers are
  npm's, but for a refusal the server makes before routing, such as a 401, which carries
  the Artifactory envelope.

### `maxUniqueSnapshots`

npm repositories ignore `maxUniqueSnapshots`, which is JFrog's stated expected behaviour:
RTFACT-27078 asks for Artifactory "to ignore this completely in cases where snapshot
policing does not apply", and RTFACT-30672 says the "parameter should not be considered
for NPM repository" (R25 2.1). An npm repository still stores the field and the v1 read
echoes it, as 7.x does, but nothing deletes by it, and the v2 read leaves it out as a field
that does not apply to npm (decision [0003](0003-repository-model.md)) [I]. 7.x has an open
known issue, RTDEV-45622 (RTFACT-27078, from 7.35.4), in which the setting can delete npm
artifacts; artifactweave does not reproduce it (#518).

### Errors, other repositories and paths not served

- **The envelope:** every error of the registry uses npm's `{"error":"<message>"}`
  (`internal/server/apierror`). The configuration operations `api/npm/auth` and
  `{repoKey}/auth/{scope}` beside it use the Artifactory envelope (Login and tokens above).
- **The reindex, migrate and resume operations** answer in the Artifactory envelope
  instead, as under "Strict layout, conversion and reindex".
- **Other repositories:** a remote or virtual npm repository answers 501 in that envelope
  until P9 and P10 (decision 0032).
- **Staged publishing,** `POST /-/stage/package/...`, and web login, `POST /-/v1/login`,
  until #262, answer 405 in the envelope, since no route takes `POST`.
- **Paths not served** answer 404 in the envelope:
  - `/-/npm/v1/tokens` and `/-/npm/v1/user`;
  - `/-/npm/v1/keys`;
  - the audit endpoints, which Artifactory serves only on virtual repositories (P10);
  - `/-/all`.

## Rationale

**Packuments from the tarball, not the body.** The JFrog CLI's default publish is a REST
deploy with no npm body at all (R25 8), so any design that kept the body would serve
nothing for those packages. Reading `package.json` from the tarball gives one result
whichever API stored it, and keeps the index rebuildable (decision 0032).

**Dist-tags and deprecation as properties.** Artifactory keeps dist-tags as `npm.disttag`
properties and recomputes them on property changes (R25 5), and `jf npm publish --tag`
sets one through the REST API. Deprecation follows the same model. It is the one piece of
version state a client changes after publishing, and Artifactory 7.x keeps it the same way,
as the `npm.deprecated` property (R25 5).

**`latest`.** 7.x stores `latest` as a dist-tag and moves it by publish, tag and removal
(R25 7), so storing it the same way gives what 7.x gives: a tagged publish of a higher
version leaves `latest` (RTFACT-24072), an `npm dist-tag add` lasts until an untagged
version outranks it, and AQL and the property API see `npm.disttag=latest` on the
tarball, as RTFACT-30153's query does. Pre-releases rank below releases so that a beta
deployed without `--tag`, which a REST deploy cannot carry, does not become what
`npm install <name>` resolves to (RTFACT-30783).

**Dist-tags and deprecation leave with overwritten content.** An overwrite with other
content leaves a file none of its properties, as 6.20's does for every package type
(decision [0004](0004-storage-sql-metadata-and-blobs.md)), so the npm format needs no rule
of its own. Kept, the tags and deprecation of the version an overwrite drops would stay on
a file that names another version, or none. They have no effect there, since the file is
not indexed, until a conversion or a move lands it on its own canonical path, where rule 1
would make its version `latest`, and its packument would show it deprecated, without
anyone having said so. Tags the write sets itself are the new content's, and stay.

**Format settings.** `npm.tag_latest_by_publish` changes what every write does to
`latest`, whatever route carries it, and what a read resolves, and `npm.enforce_path`
which uploads are admitted. The formats' settings (`formats.Settings`, one field per
format that takes any) are therefore carried by the format's handler, which every item
service the server builds, and the work queue's, already takes from one place, rather
than read from a global the hooks would share: two servers in one process, as tests run
them, can hold different settings, and a later format option takes a field beside npm's.

**Enforce path by file name.** JFrog documents the check as one of "file names" against
"the internal metadata of the package", applied to uploads, and keeps it apart from strict
layout, which stores a noncompliant upload unindexed (npm-repositories). Comparing the
whole canonical path would make the setting a second, stricter strict layout that no
source describes. JFrog added it against "path confusion", where the npm manifest names
another package than the tarball's `package.json` (JFrog's blog on npm manifest
confusion, 2023-07-20); a publish here takes its path from the tarball's own
`package.json` and refuses a body that names another package, so that case cannot arise.

**npm ignores `maxUniqueSnapshots`.** JFrog lists npm's cleanup as an open bug and states
the intended behaviour as ignoring the setting (RTFACT-27078, RTFACT-30672); the bug's
reported effect deleted a release, 1.0.2 of a scoped package. Following the stated
intention is not a deviation, and reproducing a deletion nobody asked for would put
releases at risk.

**`_rev`.** 7.x answers `1-0` in every capture (RTFACT-30472, RTFACT-29708), and npm sends
the `_rev` it read back in an unpublish's path (RTFACT-17749, RTFACT-6844). A client that
compares packuments, or a tool that stores the `_rev`, sees what it sees from 7.x, and a
`<rev>` compared with nothing refuses nothing 7.x would accept (#290).

**Queued reindex and conversion.** 7.x schedules both and answers at once (R25 6); the
work queue (decision 0033) gives them retries, parking and resume, and keeps a large
repository's rebuild out of the request. A conversion reports what it skipped by failing,
so the queue's own log, retries and parked state carry the report, and resume, which 7.x
offers for a failed conversion, has something to resume.

**Strict layout without a switch.** No source shows the repository field that carries it.
Its default for new repositories is on, and every repository here is new (R25 6).

**Search from the package index.** The index every deploy keeps current for packuments
already holds what a search matches, so a second index calculated later would add only
the delay. Reading it as the caller sees it, version by version, keeps a search from
naming a version the caller could not install.

**Login as a password login.** Legacy login turns a password into a month-long token, so
it must refuse every password a Basic login refuses, and count every wrong one: otherwise
it would be a way round the lock and the suspension. `token.allow_basic_auth` stays with
the Access token API because holding npm login to it would break `npm login` on every
default instance, which 7.x does not, as the same reasoning keeps the legacy token route
open (decision 0005). Reading no credentials on `/-/user/` follows from npm sending a stale
token with the login that replaces it.

**`api/npm/auth` writes back nothing new.** The answer is pasted into `.npmrc` files and CI
logs. A caller that sent its password gets the encrypted password 7.x documents, which
the password's next change revokes (DV-004), not the password; one that sent a token gets
that token, which it holds already.

**Three choices depart from Artifactory** and are in the
[deviations register](../../implementation/deviations.md):
- strict layout has no switch (DV-041);
- npm metadata is computed from the package index rather than kept under `.npm/` (DV-042);
- a search finds a package once its publish commits, rather than once an asynchronous
  index catches up (DV-071).

**Alternatives considered:**
- *Storing the publish body as the version's metadata:* it is absent for REST deploys and
  can disagree with the tarball, which is what npm installs.
- *`latest` from the publish body, as npm's registry does:* every publish would pin
  `latest`, and the documented highest-SemVer default would never apply.
- *`latest` computed on every read*, as this decision first planned: a tagged publish of a
  higher version would become `latest`, where 7.x leaves it (RTFACT-24072), and no
  property would show it; the maintainer chose 7.x's stored tag (2026-10-18).
- *A `_rev` built from the version set*, `<number of versions>-<32 hex digits of a hash>`,
  which would refuse an unpublish that races a publish: 7.x answers `1-0`, and the
  maintainer chose 7.x's answer (2026-10-18).
- *A `.npm/` packument file per package:* a read-modify-write file under concurrent
  publishes, in a format no source shows.

## Constraints

- **Not in packuments:** `readme` and `maintainers` are left out, as 7.x leaves them out
  (RTFACT-30472), and `users` is always empty.
- **Pinning `latest`:** `npm publish --tag latest --force` of a lower version does not move
  `latest`; `npm dist-tag add` does, until an untagged version that outranks it is
  published. How long such a `latest` lasts on 7.x across publishes, reindex, copy, move
  and delete, which version 7.x picks when every version is a pre-release, and what it
  answers `npm dist-tag rm latest` are inferred [I].
- **A version published during an unpublish:** npm's unpublish `PUT` sends the versions to
  keep, and its `_rev` cannot show that the client's view is stale, so a version published
  between the client's read and that `PUT` is removed with the versions it meant to remove.
  7.x's constant `_rev` leaves it the same risk (#290); that 7.x then removes the new
  version too is inferred [I].
- **Conversion reports:** a tarball the conversion cannot move is named in the conversion's
  failure, which the work queue logs and keeps on the parked item; no API lists it.
- **Tags on a tarball off its canonical path:** a tag set on a stray tarball, and not
  cleared by an overwrite with other content, reaches whatever version the conversion
  later finds in it (rule 1).
- **A rebuild of a version:** a REST deploy of other content over a version's tarball takes
  its dist-tags and deprecation, so a `latest` pinned to it by `npm dist-tag add` moves by
  rule 4.
- **Enforce path:** a tarball named rightly but off its canonical path passes
  `npm.enforce_path` and is stored unindexed, as strict layout stores it; a copy or move
  is not checked.
- **A package named `auth`:** its version manifests cannot be read by
  `GET /auth/<version>`, which is the JFrog `auth/<scope>` operation. Its packument and
  tarballs are unaffected, and npm installs from those.
- **Login:** a token issued by legacy login lasts `npm.login_token_expiry`, and a web login
  waits for #262.
- **Unconfirmed:** what Artifactory answers for every item in R25 section 10 that the audit
  (#378) did not settle is inferred, and on the live-comparison list (#216) for P19.
