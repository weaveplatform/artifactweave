# 0034: npm local repositories

Status: Proposed

## Context

npm, pnpm, Yarn and the JFrog CLI publish and install packages through the npm registry
protocol, which Artifactory serves at `/artifactory/api/npm/<repo>/`. Artifactory stores
each version as a tarball in the repository tree and keeps dist-tags as properties on the
tarballs, so the JFrog CLI can publish by an ordinary REST deploy and still be seen by
`npm install`. Decision [0032](0032-package-format-handlers.md) fixes how a format plugs
into the item service and the protocol router kit; this decision fixes what the npm
registry answers for a local repository and what it stores.
[Research 25](../25-npm.md) holds the facts, and its section numbers are cited below as R25.

## Decision

### Routes and names

- The registry is `/artifactory/api/npm/{repoKey}/`, mounted through the router kit of
  decision 0032. The JFrog operations beside it (`POST .../reindex`,
  `GET .../auth/<scope>`) stay with the generated servers.
- A package name that begins with `@` takes two path segments, however its slash and `@`
  are percent-encoded: npm sends `@scope%2fname` (R25 1), and a slash that arrives
  unencoded is accepted too.
- After the name:
  - nothing is the packument;
  - `/<version or tag>` is one version manifest;
  - a path with a `-` segment is a tarball, served from the item at that path through
    `ServeItem`, so download counts and redirects apply;
  - `/-rev/<rev>` is an unpublish step.

### Storage and properties

The canonical path of a tarball comes from the `package.json` inside it:
`<name>/-/<name>-<version>.tgz`, and for a scoped package
`@scope/name/-/@scope/name-<version>.tgz`. These are the paths npm names in its publish
body and the JFrog CLI deploys to (R25 2.1, 8). The version is `package.json`'s, cleaned as
npm's `semver.clean` cleans it: a leading `v` or `=` dropped, and build metadata too, which
npm ignores. It must be valid SemVer; otherwise the tarball is not indexed. The name must be
one npm accepts for an existing package (`validate-npm-package-name`'s
`validForOldPackages`).

**Reading the tarball.** On a `.tgz` whose path could be canonical, the npm format's
`Inspect` reads the tarball once, outside the write's transaction:
- `package.json` is the one directly inside the top-level folder, whatever that folder is
  called. npm strips that folder when it extracts, so a later entry of the same name replaces
  an earlier one, as it does here.
- `fileCount` and `unpackedSize` count the regular files; folders and links are not counted.
- `hasInstallScript` is true when `scripts` has a `preinstall`, `install` or `postinstall`
  script, or when the package has a `binding.gyp` and `gypfile` is not `false`, since npm
  then runs `node-gyp rebuild`.
- The read is bounded: a tarball of more than 2^20 entries, one that inflates past 16 GiB,
  or whose `package.json` is over 1 MiB is stored but not indexed.

If the tarball is at its canonical path, the hooks:
- link the package and the version in the package index (decision
  [0018](0018-package-index.md));
- set `npm.name`, `npm.version`, and, when `package.json` has them, `npm.description` and
  `npm.keywords`. Keywords are one value, a JSON array of strings (R25 5).
  - The stores cut every property value to 4000 UTF-16 code units, as Artifactory does
    (#338), so a long description is cut too. The keywords leave out those that do not fit,
    so `npm.keywords` stays a JSON array. The full text stays in the per-version document
    below.
  - An overwrite with a `package.json` that no longer has a description or keywords removes
    them.

These properties are set by the format and need no Annotate. A file at the path that is no
longer that version's tarball, such as one overwritten with another version's content,
drops the version from the index.

**Two more properties are the state npm changes after a publish:**
- `npm.disttag`, multi-valued, one value per tag (R25 5);
- `npm.deprecated`, the deprecation message. An empty message removes it.

Either may be changed through the npm protocol or the JFrog property API. The format's
`Annotated` hook (decision 0032) re-indexes the version on every change, by either route.
When a tarball gains a tag, the hook removes that tag from the package's other tarballs in
the same transaction, so a tag names one version.

**The per-version document** is `PackageVersion.Metadata` (`pkg/types/version.go`). It
caches:
- `package.json`;
- the `dist` facts: `shasum` from the stored SHA-1, `integrity` from the stored SHA-512
  (decision 0032, #296), `fileCount` and `unpackedSize`;
- `hasInstallScript`;
- the version's tags and deprecation;
- its deploy time.

Packuments and search read the index and this cache, not the publish body. Nothing is
stored under `.npm/` (DV-042). Everything indexed follows from the tarballs and their
properties, so a reindex, a replica and a federation member reach the same packuments.

### Packuments

- **The full packument** (`application/json`):
  - `_id`, `_rev`, `name`, `description` (from `latest`), `dist-tags`;
  - `versions`, each the cached `package.json` with `_id` (`<name>@<version>`), `dist`
    and `deprecated`;
  - `time`, with `created`, `modified` and one entry per version.
- **The abbreviated packument** (`application/vnd.npm.install-v1+json`) has the fields
  npm's metadata document lists for it (R25 3): `name`, `modified`, `dist-tags`, and per
  version the dependency fields, `bin`, `engines`, `os`, `cpu`, `deprecated`,
  `hasInstallScript` and `dist`.
- **Which form:** the abbreviated one when it is the first type `Accept` lists, the full
  one otherwise. A `?write=true` read is always the full one.
- **`dist.tarball`** is built on each request from the base URL (#315) as
  `<base>/artifactory/api/npm/<repo>/<canonical path>`, and is never stored.
- **`_rev`** is `<number of versions>-<the first 32 hex digits of SHA-256 over the sorted
  version strings>`. It changes when a version is published or removed, and not when a tag
  or a deprecation changes.
- **Readable versions only:** a version whose tarball the caller cannot read is left out,
  with the tags that name it. A package with no readable version is answered as the item
  routes answer an unreadable path.

### Publishing

`PUT /<name>` whose body has `_attachments` is a publish (R25 2.1):
- **Streaming:** the body is read as a stream. The attachment's base64 is decoded straight
  into the blob store, whatever order the body's fields come in. The request may be at
  most `npm.max_publish_size` (default `1GiB`); a larger one answers 413.
- **Shape:** the body must name exactly one version, and the name in the URL, `_id` and
  `name` must agree. Exactly one attachment's name must end in `.tgz`; other attachments,
  such as a provenance bundle, are not stored.
- **Validation:** the tarball's `package.json` must give the body's name and version.
  `length` must equal the decoded size, and `dist.shasum` and each `dist.integrity` hash
  the server computes must match. Any failure answers 400.
- **Republish:** a version that already exists, or whose canonical path holds an item,
  answers 403 for every caller, administrators included, as Artifactory does (R25 2.1).
  npm 11 and later refuse such a publish before sending it unless `--force` is given.
- **Tags:** the body's dist-tags other than `latest` are stored as `npm.disttag` on the new
  tarball, which moves them from older versions. The body's `latest` is not stored (below).
  The tags a publish sets need Deploy, not Annotate.
- **Success** answers 200 with `{"ok":true}`. npm ignores the body (R25 2.1).
- **Other routes:** a REST deploy of a tarball (`jf npm publish`, `jf rt u`) is an ordinary
  item deploy. Overwriting needs Delete, as for any item, and the hooks re-index the new
  content. `POST /-/stage/package/...` (`npm publish --stage`) is not served.

### Dist-tags and `latest`

- **The operations** (R25 2.2):
  - `GET /-/package/<name>/dist-tags` answers `{tag: version}`.
  - `PUT /-/package/<name>/dist-tags/<tag>`, with a JSON-string version, sets
    `npm.disttag=<tag>` on that version's tarball and removes the tag from the others.
  - `DELETE /-/package/<name>/dist-tags/<tag>` removes the tag.
- **Statuses:**
  - each operation answers 200 with the resulting `{tag: version}` map;
  - an unknown package, version or tag answers 404;
  - a tag that is a valid SemVer range answers 400, matching the check the client makes
    before sending (R25 2.2).
- **`latest`** is resolved on every read, in this order:
  1. the version whose tarball carries `npm.disttag=latest` (a pin);
  2. with `npm.tag_latest_by_publish: true`, the version deployed most recently
     (Artifactory's `artifactory.npm.tag.tagLatestByPublish`, R25 7);
  3. the highest version by SemVer that is not a pre-release, or the highest version when
     every version is a pre-release.
- **When a pin clears:** a new version that would be `latest` under rule 2 or 3 removes an
  existing pin, so a pin set to roll back a bad release lasts until the next release that
  outranks it.
- **Why a publish's `latest` is dropped:** every npm publish names `latest` unless `--tag`
  is given, so storing it would make every published version a pin. The documented default,
  the highest SemVer (R25 7), could then never apply.

### Deprecation and unpublish

- **Packument updates:** `PUT /<name>` without `_attachments` is a packument update, as
  `npm deprecate` sends it (R25 2.2).
  - Only each version's `deprecated` is applied: the format sets, changes or removes
    `npm.deprecated` on that version's tarball.
  - Versions missing from the body are left alone, and other fields are ignored.
  - It needs Annotate on each tarball that changes, and answers 200 `{"ok":true}`.
- **Unpublish** follows npm's flows (R25 2.2):
  - `PUT /<name>/-rev/<rev>` removes the versions missing from the body.
  - `DELETE /<name>/-rev/<rev>` removes every version.
  - `DELETE /<tarball path>/-rev/<rev>` removes that tarball.
  - Each removal goes through the trash can and needs Delete on the tarball. Tags on a
    removed version go with it.
  - Dist-tags and other fields in the `PUT` body are ignored: the client computes `latest`
    with prereleases included, and the server's rule applies instead.
  - A tarball already gone answers 404, which npm treats as done.
- **`_rev` is enforced** on `/-rev/` requests: a `<rev>` that is not the package's current
  `_rev` answers 409. The version set it names is the one the client saw, so a version
  published since is never removed by mistake. A packument update carries no `_rev` and is
  not checked.

### Search, ping and whoami

- **`GET /-/v1/search?text=&size=&from=`** reads the package index and the per-version
  cache:
  - The first three whitespace-separated terms of `text` must each appear, ignoring case,
    in the name, description or keywords of the package's `latest`. How many terms
    Artifactory accepts is inferred (R25 3).
  - `size` defaults to 20 and is capped at 250; `from` defaults to 0. Results are ordered
    by name. `quality`, `popularity` and `maintenance` are ignored.
  - The body is
    `{"objects":[{"package":{"name","scope","version","description","keywords","date","links"},"score":{"final":1,"detail":{"quality":1,"popularity":1,"maintenance":1}},"searchScore":1}],"total","time"}`.
  - Packages the caller cannot read are left out.
  - A publish is searchable once it commits. Artifactory calculates its search index
    asynchronously (R25 3); here the deploy keeps the index current, so no work queue is
    involved (decision 0032).
- **`GET /-/ping`** answers 200 `{}` to any authenticated caller, and to anonymous callers
  when anonymous access is on (R25 3).
- **`GET /-/whoami`** answers `{"username":"<name>"}`, or 401 to an anonymous caller. npm
  calls it only when it holds a token (R25 3).

### Login and tokens

On `/-/user/` paths, anonymous requests are accepted, and credentials that fail to
authenticate are treated as anonymous rather than refused. Artifactory lets anonymous
requests reach the same paths (R25 4).

- **Legacy login,** `PUT /-/user/org.couchdb.user:<user>`:
  - checks `password` as a password login for the user the URL names; the body's `name`
    must match it (400 otherwise);
  - on success answers 201 `{"ok":true,"id":"org.couchdb.user:<user>","token":"<token>"}`;
  - the token is a revocable access token of decision
    [0005](0005-authentication-and-tokens.md), with the user's own permissions;
  - the token expires after `npm.login_token_expiry` (default `720h`), as an hourly
    `npm login` would be unusable;
  - a wrong password or an unknown user answers 401, never 400 or 409. npm reports a 400
    as "no such user", which would reveal which names exist, and it reads a 409 as "update
    the user", which is not served. A transient user cannot log in (R25 4).
- **Web login:** `POST /-/v1/login` answers 404 in the npm envelope until #262, so npm
  falls back to legacy login (R25 4).
- **Logout,** `DELETE /-/user/token/<token>`:
  - revokes the named token when it is a revocable access token, since holding it proves
    the right to end it;
  - answers 200 `{"ok":true}` in every case, because npm keeps the stale token in `.npmrc`
    unless logout succeeds (R25 4).
- **`GET /artifactory/api/npm/auth`** answers `text/plain` `.npmrc` lines (R25 4, the body
  is inferred). An anonymous caller gets 401.
  - A caller with Basic credentials gets `_auth = <base64 of the credentials sent>`,
    `always-auth = true` and `email = <the user's email>`.
  - A caller with a Bearer token gets `_authToken = <the token>`.
- **`GET /artifactory/api/npm/<repo>/auth/<scope>`** answers the same lines, prefixed with
  `@<scope>:registry=<registry URL>` and keyed to that registry. It is in the OpenAPI
  sources as `x-unverified`.
- **Not served:** `/-/npm/v1/tokens` and `/-/npm/v1/user`, which npm calls for `npm token`
  and `npm profile`, answer 404 until P19 finds whether Artifactory serves them (R25 4).

### Strict layout, conversion and reindex

- **Strict layout:** every npm local repository behaves as one with "Enforce strict
  layout" on, which is Artifactory's default for a new repository (R25 6). There is no
  switch (DV-041).
  - A `.tgz` at a path other than its canonical one, or one without a readable
    `package.json`, is stored but not indexed. It can still be downloaded at its path.
- **Enforce path:** `npm.enforce_path: true` (default `false`), the equivalent of
  `artifactory.npm.enforce.path`, refuses such a deploy with 400 in every npm local
  repository.
- **Conversion:**
  - `POST /api/v1/migrations/npm/repositories/<repo>/migrate` queues a conversion on the
    work queue (decision [0033](0033-persistent-work-queue.md)), keyed by repository, and
    answers 202.
  - The conversion moves each tarball that is not indexed, but whose `package.json` gives
    a canonical path, to that path. A canonical path already taken is skipped and
    reported. The run is idempotent.
  - `.../resume` requeues a conversion that failed (a parked work item) and answers 202,
    or 400 when there is none to resume.
  - The response bodies are inferred (R25 6).
- **Reindex:** `POST /api/npm/<repo>/reindex` queues the format's `Reindexer` (decision
  0032) for the repository and answers 200 in plain text. It rebuilds the index and the
  per-version cache from the tarballs and their properties.
- **Which repositories:** all three operations need Manage and act on npm local
  repositories only; any other repository answers 400.

### Permissions

| Operation | Needs |
|---|---|
| Packument, version manifest, dist-tag list | Read on a version's tarball; unreadable versions are left out |
| Tarball download | Read on the tarball |
| Publish | Deploy on the canonical path |
| Dist-tag add or remove | Annotate on each tarball that gains or loses the tag |
| Deprecate | Annotate on each tarball that changes |
| Unpublish | Delete on each tarball removed |
| Search | Read; unreadable packages are left out |
| Ping | Any authenticated caller, or anonymous when anonymous access is on |
| Whoami, `api/npm/auth` | An authenticated caller |
| Login, logout | None |
| Reindex, migrate, resume | Manage on the repository |

### Errors, other repositories and paths not served

- **The envelope:** every npm error uses `{"error":"<message>"}`
  (`internal/server/apierror`).
- **Other repositories:** a remote or virtual npm repository answers 501 in that envelope
  until P9 and P10 (decision 0032).
- **Paths not served** answer 404 in the envelope:
  - staged publishing;
  - web login until #262;
  - `/-/npm/v1/tokens` and `/-/npm/v1/user`;
  - `/-/npm/v1/keys`;
  - the audit endpoints, which Artifactory serves only on virtual repositories (P10);
  - `/-/all`.

## Rationale

**Packuments from the tarball, not the body.** The JFrog CLI's default publish is a REST
deploy with no npm body at all (R25 8), so any design that kept the body would serve
nothing for those packages. Reading `package.json` from the tarball gives one result
whichever API stored it, and keeps the index rebuildable (decision 0032).

**Dist-tags and deprecation as properties.** Artifactory keeps dist-tags as `npm.disttag`
properties and recomputes them on property changes (R25 5), and `jf npm publish --tag`
sets one through the REST API. Deprecation follows the same model. It is the one piece of
version state a client changes after publishing, and Artifactory's storage for it is
unknown (R25 10).

**`latest`.** The order follows the documented default and the documented system property
(R25 7). Pre-releases are kept out of the computed `latest` so that a beta deployed without
`--tag`, which a REST deploy cannot carry, does not become what `npm install <name>`
resolves to.

**`_rev`.** npm's unpublish sends the versions to keep, not the one to remove. Without a
check, a version published between the client's read and its `PUT` would vanish. A
revision built from the version set refuses exactly that case and leaves tag and
deprecation changes, which cannot cause it, free of conflicts.

**Strict layout without a switch.** No source shows the repository field that carries it.
Its default for new repositories is on, and every repository here is new (R25 6).

**Two choices depart from Artifactory** and are in the
[deviations register](../../implementation/deviations.md):
- strict layout has no switch (DV-041);
- npm metadata is computed from the package index rather than kept under `.npm/` (DV-042).

**Alternatives considered:**
- *Storing the publish body as the version's metadata:* it is absent for REST deploys and
  can disagree with the tarball, which is what npm installs.
- *`latest` from the publish body, as npm's registry does:* every publish would pin
  `latest`, and the documented highest-SemVer default would never apply.
- *Accepting any `_rev`:* simpler, and nothing confirms that Artifactory checks it, but it
  loses versions under concurrent publish and unpublish.
- *A `.npm/` packument file per package:* a read-modify-write file under concurrent
  publishes, in a format no source shows.

## Constraints

- **Not in packuments:** `readme`, `maintainers` and `users` are left out.
- **Pinning `latest`:** `npm publish --tag latest --force` of a lower version does not move
  `latest`; `npm dist-tag add` does.
- **A package named `auth`:** its version manifests cannot be read by
  `GET /auth/<version>`, which is the JFrog `auth/<scope>` operation. Its packument and
  tarballs are unaffected, and npm installs from those.
- **Login:** a token issued by legacy login lasts `npm.login_token_expiry`, and a web login
  waits for #262.
- **Unconfirmed:** what Artifactory answers for every item in R25 section 10 is inferred,
  and on the live-comparison list (#216) for P19.

## Verification

- **Unit tests** for:
  - each publish refusal (400, 403 for an administrator too, 413), and a large synthetic
    tarball published without being held in memory;
  - the `latest` order and pin clearing, dist-tag moves, deprecation round trips;
  - the three unpublish flows with a stale `_rev`;
  - full and abbreviated packuments as golden files, and scoped names encoded and
    unencoded;
  - search terms and paging;
  - login, logout and both `api/npm/auth` forms.
- **The npm rows** of the status table and the route × principal matrix (decision 0032).
- **Format tests:** `formattest` for the npm format: the index after deploy, overwrite,
  delete, copy, move, restore and property changes, and a reindex that reproduces it.
- **Acceptance (#270)** with npm 12:
  - `npm publish`, `install`, `dist-tag`, `deprecate`, `unpublish`, `search`, `login`,
    `logout`, `ping` and `whoami`;
  - `jf npm publish`, with and without `--run-native` and `--tag`;
  - `jf npm install` with Basic credentials, which calls `api/npm/auth`;
  - the conversion of a tarball deployed with `jf rt u` to a non-canonical path.
