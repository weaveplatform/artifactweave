# 0037: PyPI local repositories

Status: Proposed

Checked against: **Artifactory 7.161.32** (SaaS 7.174.0) on 2026-10-19 ([research 28 section 16](../28-pypi.md#16-artifactory-7x-check), [#527](https://github.com/weaveplatform/artifactweave/issues/527)).

## Context

pip, uv, Poetry, Pipenv and twine install and publish Python packages through the simple
repository API and the legacy upload API, which Artifactory serves at
`/artifactory/api/pypi/<repo>/`. Artifactory indexes a distribution by the metadata inside it
wherever it is stored, keeps that metadata as `pypi.*` properties, and computes the index
pages from them. Decision [0032](0032-package-format-handlers.md) fixes how a format plugs into
the item service and the protocol router kit; this decision fixes what a PyPI local repository
stores, indexes and answers. [Research 28](../28-pypi.md) holds the facts, cited below as R28
with its section numbers. The implementation is #537 (the format), #538 (the simple index),
#539 (upload) and #540 (the JSON API and reindex), with #516 for the queued reindex.

## Decision

### Routes

The registry is `/artifactory/api/pypi/{repoKey}`, mounted through the router kit by
`internal/server/pypi`, for local and federated repositories:

| Method and path | Answer |
|---|---|
| `GET`, `HEAD` `/simple` | 302 to `/simple/` |
| `GET`, `HEAD` `/simple/` | The project list |
| `GET`, `HEAD` `/simple/<name>` and `/simple/<name>/` with `<name>` not normalised | 302 to `/simple/<normalised>/` |
| `GET`, `HEAD` `/simple/<normalised>/` | The project page |
| `GET`, `HEAD` `/pypi/<name>/json`, `/pypi/<name>/<version>/json` | The JSON API |
| `POST` `/` (with or without the trailing slash) | An upload |
| `POST` `/reindex` | The reindex |
| `GET`, `HEAD` `/<path>` | The item at `<path>`, or the core metadata of the wheel at `<path>` less `.metadata` |
| `PUT` `/<path>` | A REST deploy of `<path>`, as `/artifactory/<repo>/<path>` (R28 2, RTFACT-29834) |
| `POST` to any other path | 405 |
| Any other method | 405 |

Every `Location` comes from the base URL resolver of decision
[0002](0002-spec-first-flat-crud-handwritten-item-paths.md): `X-JFrog-Override-Base-Url`, then
the configured `base_url`, as JFrog intends (RTFACT-31494), then the forwarded headers. Links
inside the pages are relative, so they need no base URL.

### Projects, versions and the canonical path

- **A project** is a PEP 503 normalised name: lower case, every run of `.`, `-` and `_` one
  `-` (R28 2). Every file whose metadata names normalise alike belongs to one project, as
  7.x's lookup by `pypi.normalized.name` finds them (RTFACT-29892). What JFrog's note that
  `jfrog.pypi` and `jfrog_pypi` "will not be aggregated" changes in 7.x's answers is inferred
  [I] and on #216.
- **A version** is the metadata's `Version` in its PEP 440 normalised form, or as written when
  PEP 440 cannot read it. Versions are ordered by `types.ComparatorFor(repo.PyPI)`.
- **The canonical path** of an upload through the upload API is
  `<normalised name>/<Version as the metadata writes it>/<file name as sent>`. 7.x stores
  twine uploads at `<name>/<version>/<file>` with `-` for `_` in the folder (RTFACT-20390,
  RTFACT-29973); for names in lower case without dots, the vast majority, the two agree. 7.x's
  folder for upper case and dots is inferred [I] and on #216.

### Which files are indexed

A file is in the package index when:
- its name ends in `.whl`, `.tar.gz`, `.tgz`, `.tar.bz2`, `.tar`, `.zip` or `.egg`, the types
  7.x extracts metadata from (R28 6); and
- its content yields core metadata with a `Name` and a `Version`, or, when it does not, the
  file carries both `pypi.name` and `pypi.version`, which JFrog requires of manual uploads it
  cannot read (R28 6). A `Name` that is no valid project name (PEP 508), or a `Version` that is
  no single path segment of at most 256 printable characters without space, counts as none, so
  neither can name another folder of the canonical path [I].

**Wherever the file is stored.** An off-canonical wheel deployed by REST, copied or moved is
indexed by its metadata, as 7.x indexes it (RTFACT-29892, RTFACT-20305, RTFACT-30372). There is
no strict layout. A file that meets neither condition is stored and not indexed.

**At once.** The index is updated in the write's own transaction, so a package can be installed
as soon as its upload answers. 7.x waits for a 60-second quiet period after the last upload to
the repository before it indexes ([D] pypi-repositories; 6.20 `pypi.index.quietPeriodSecs`,
R28 6).

**Reading the metadata** (`Inspect`, before the write's transaction, through `archive` with
npm's limits: 2^20 entries and 16 GiB inflated; a header block over 1 MiB leaves the file
unindexed):
- a wheel: `METADATA` in the top-level `*.dist-info/` folder, the one named for the file's
  distribution and version when there are several;
- an sdist (`.tar.gz`, `.tgz`, `.tar.bz2`, `.tar`, `.zip`): `PKG-INFO` at the root, else in the
  single top-level folder, the root preferred, as 7.x (RTFACT-17032, RTFACT-16868);
- an egg: `EGG-INFO/PKG-INFO`;
- the fields are the header block only, up to the first blank line, as RFC 822 headers with
  continuation lines (RTFACT-18571).

### Properties and yanking

On every indexed file the format writes, without needing Annotate:
- `pypi.name` (the metadata's `Name` as written), `pypi.version`, and `pypi.summary` when the
  metadata has a `Summary` (R28 6);
- `pypi.normalized.name`, and `pypi.requires.python` when the metadata has `Requires-Python`,
  as 7.x keeps them (RTFACT-29892).

Content wins: a deploy whose own `pypi.*` matrix parameters disagree with the content gets the
content's values. A file indexed by its properties alone keeps them, and takes its
`Requires-Python` from `pypi.requires.python`, which the 7.x query reads [I]. An overwrite with other
content clears the file's properties, as for every package type (decision
[0004](0004-storage-sql-metadata-and-blobs.md)).

**Yanking** is the property `pypi.yanked`, which the 7.x query reads (RTFACT-29892; the
7.84.10 note calls it "the `yanked` property"). A file is yanked when the property is set to
anything but `false` (any case); a value of `true` or an empty value is a yank without a reason,
any other value is the reason. The format's `Annotated` hook (decision 0032) re-indexes the file
whenever `pypi.yanked`, `pypi.name` or `pypi.version` changes, so the pages follow at once, and
`pypi.requires.python` for a file indexed by its properties alone. For a file whose content
names its project, the content decides, so a change to `pypi.name`, `pypi.version` or
`pypi.requires.python` leaves it where it is.
Setting it needs Annotate, as any property does. The values 7.x writes are inferred [I].

### Settings

Four server-wide settings, each in `formats.Settings.PyPI` (`pypi.Settings`), each off by
default as its 7.x counterpart is, each read by every PyPI repository:

| Key | Environment variable | Default | 7.x behaviour it mirrors |
|---|---|---|---|
| `pypi.enforce_layout` | `ARTIFACTWEAVE_PYPI_ENFORCE_LAYOUT` | `false` | The system property `artifactory.pypi.enforce.layout` (R28 7) |
| `pypi.enforce_naming_normalization` | `ARTIFACTWEAVE_PYPI_ENFORCE_NAMING_NORMALIZATION` | `false` | The system property `artifactory.pypi.enforce.naming.normalization` (R28 7) |
| `pypi.simple_json` | `ARTIFACTWEAVE_PYPI_SIMPLE_JSON` | `false` | "Enable simple json format" in Packages Settings, from 7.146.7 (R28 3) |
| `pypi.core_metadata` | `ARTIFACTWEAVE_PYPI_CORE_METADATA` | `false` | The system property that turns on PEP 658, "Fast Dependency Resolution" (RTFACT-31470); its name is inferred [I] (R28 4) |

They go in `internal/config/pypi.go`, under a `pypi:` block of the YAML configuration, with a
row each in the configuration reference.

### Enforce layout and naming normalisation

Both check uploads to local and federated repositories: a REST deploy (including `PUT` under
`/api/pypi/`), a checksum deploy, an archive's entry and an upload through the upload API. They
check files whose names end in the extensions above. Files stored before a setting was turned on
stay. Copies and moves are not checked, as npm's `npm.enforce_path` does not check them (decision
[0034](0034-npm.md)); what 7.x does is inferred [I].

- **Naming normalisation** refuses a file whose name segment holds a `-` (R28 7). The name
  segment is what precedes `-<Version>` in the file name, with the metadata's `Version`; when
  the content yields none, a wheel must have five `-`-separated fields, or six with a build tag
  that begins with a digit, and any other type's part before its last `-` must hold no `-`.
  It answers 403
  `Action prevented due to artifact file name normalization requirements - artifact name <file name> does not conform to normalized requirements`.
- **Enforce layout** compares the file name with the metadata literally, as JFrog's table
  shows (R28 7): the file name must begin `<Name>-<Version>`, with the metadata's `Name` and
  `Version` exactly as written, followed by `-` for a wheel or an egg and by the extension
  otherwise. It answers 403
  `Action prevented due to Enforce Layout policy - package file name/version <file name> does not match the package internal name/version <Name>/<Version> in the metadata file`,
  without the `” +` that JFrog's documented text carries from its source, and 403
  `Action prevented due to Enforce Layout policy - could not find metadata file to compare`
  when the content yields no metadata.
- **With both on**, naming normalisation is checked first, since it rests on the file name.
  Which check 7.x answers first, and what it puts in place of `<ARTIFACT_NAME>`, are inferred
  [I].
- **Consequence:** with enforce layout on, a package whose metadata name holds a `-` cannot be
  uploaded with the `_` that current build tools put in its file names, as JFrog's table
  refuses `jfrog_pypi-1.0.0.tar.gz` for `jfrog-pypi`.

### Reserved namespaces

`packages/**` and `simple/**` are refused with 400 in every PyPI repository, as 7.x refuses
deploys there (R28 6): uploads of every kind, and copies and moves into them, because JFrog keeps
them for "internal logic" and a file under `simple/` could not be served by the API.
RTFACT-30372 shows 7.49.8 accepting a copy from a remote cache into a local repository's
`packages/`; whether 7.161 still does is inferred [I] and on #216. The message is
`The repository '<repo>' rejected '<path>': packages/ and simple/ are reserved in a PyPI repository.`
[I]. A project normalised to `packages` or `simple` therefore cannot be uploaded through the
upload API (its canonical folder is reserved) and answers the same 400.

### The simple index

**HTML,** always available, with `Content-Type: text/html` as 7.x sends it (RTFACT-29209):

```html
<!DOCTYPE html>
<html><head><title>Simple Index</title><meta name="api-version" value="2" /></head><body>
<a href="../../<path>#sha256=<hex>" data-requires-python="&gt;=3.9" data-yanked="<reason>" rel="internal"><file name></a>
</body></html>
```

- **The project page** has one anchor per indexed file the caller may read, one per line,
  without `<br />` (RTFACT-30288), ordered by version and then file name. The link is relative
  (`../../` and the item's path, each segment percent-encoded) with `#sha256=` of the stored
  content (RTFACT-18495). `data-requires-python` is present when the file has one, HTML-escaped;
  `data-yanked` when the file is yanked, empty or with its reason, HTML-escaped. With
  `pypi.core_metadata` on, a wheel with core metadata also carries
  `data-dist-info-metadata="sha256=<hex>"` and `data-core-metadata="sha256=<hex>"`.
- **The project list** has one anchor per project with a readable file,
  `<a href="<normalised>/" rel="internal"><normalised></a>`, sorted by name. 7.x's project list
  is inferred [I]; the trailing slash spares browsers a redirect, and pip and uv never read the
  list.
- **A project with no file the caller may read** answers 404, so a page never shows that a
  project exists to a caller who could not install it. A caller who may read nothing in the
  repository gets the kit's 401 (anonymous) or 403, so pip asks for credentials (RTFACT-17764).
  An empty repository's list is an empty page.

**JSON,** with `pypi.simple_json` on, `Content-Type: application/vnd.pypi.simple.v1+json`:
- the project page:
  `{"meta":{"api-version":"1.1"},"name":"<normalised>","files":[…],"versions":[…]}`. Each file
  has `filename`, `url` (the same relative link, without the fragment), `hashes`
  (`{"sha256":…}`), `requires-python` when present, `yanked` (`false`, `true` or the reason),
  `size`, `upload-time` (the file's deploy time in UTC, `yyyy-mm-ddThh:mm:ss.ffffffZ`), and,
  with `pypi.core_metadata` on, `core-metadata` and `dist-info-metadata` (`{"sha256":…}`, or
  `false` for a file without core metadata). `versions` lists the versions of the files listed.
- the project list: `{"meta":{"api-version":"1.1"},"projects":[{"name":"<normalised>"}]}`.
- API version 1.1 because its `versions`, `size` and `upload-time` are what the index already
  holds, and uv's `exclude-newer` needs `upload-time` (RTFACT-31464). What 7.x writes is
  inferred [I].

**Choosing the form.** With `pypi.simple_json` on, JSON is answered when the request's `Accept`
names `application/vnd.pypi.simple.v1+json` or `application/vnd.pypi.simple.latest+json` with
a quality above 0 and not below that of the best HTML type it accepts (`text/html`,
`application/vnd.pypi.simple.v1+html`, `application/vnd.pypi.simple.latest+html`, or a
wildcard); otherwise HTML. pip and uv rank JSON first and get it (R28 1). With the setting off,
HTML is answered whatever `Accept` says, as 7.x falls back (R28 3); nothing answers 406, which
7.x did before 7.146.7 (RTFACT-30869). The answer without `Accept` is HTML [I].

**Caching.** Both pages, in both forms, carry `Vary: Accept`, `Cache-Control: no-cache`, and
`X-Checksum-Sha1` with an `ETag` equal to it, unquoted, over the body sent, as decision 0034
gives npm's packuments; a matching `If-None-Match` answers 304 (7.98.7, RTFACT-30198,
RTFACT-29209). The `ETag` form and the `Cache-Control` value 7.x sends are inferred [I].

### Core metadata files (PEP 658)

**Behind `pypi.core_metadata`, off by default,** as 7.x keeps PEP 658 behind a system property
(RTFACT-31470). The index always keeps the core metadata, so turning the setting on needs no
reindex.

- **Which files:** wheels only, whose `METADATA` the wheel format guarantees installing does
  not change. An sdist's `PKG-INFO` may list fields as `Dynamic`, and the attribute promises an
  unchanged file (R28 4) [I].
- **What is kept:** a copy of the wheel's `METADATA`, at most 1 MiB, and its SHA-256, in the
  file's record in the package index. A larger one leaves the wheel indexed without core
  metadata.
- **Where it is served:** `GET` or `HEAD` of the wheel's path plus `.metadata` answers the copy,
  `200`, `Content-Type: application/octet-stream`, with the page caching headers above and an
  `ETag` over the copy, under the wheel's Read permission. It is computed, not an item, as
  npm's packuments are (decision 0034). While the setting is on and the wheel has core
  metadata, an item a client deploys at the `.metadata` path is not served there, so the bytes
  always match the advertised hash.
- **Off:** no attributes and no JSON keys, and a `.metadata` path is an ordinary item path.

### Downloads and deploys

`GET` and `HEAD` of `/api/pypi/<repo>/<path>` serve the item through the kit's `ServeItem`, so
`Range` (7.133.3), `ETag`, the `X-Checksum-*` headers, download statistics, redirects (decision
[0029](0029-cdn-delivery-and-download-redirect.md)) and permissions behave as every download
does. A folder answers 404. The 6.x link form `/api/pypi/<repo>/packages/<path>` is not served:
no item can sit under `packages/`, and 7.77.6 stopped serving the doubled form (RTFACT-30372).
P20/P28 must capture the legacy alias and its migration to the current download URL;
its age alone does not justify permanent exclusion.
`PUT` is the generic deploy, with the enforcement settings and the reserved namespaces applied
through `Admit`.

### Upload

`POST /api/pypi/<repo>` or `/api/pypi/<repo>/`, `multipart/form-data`, Basic authentication with
a password or a token as the password. Checked in this order:

| Check | Answer |
|---|---|
| The repository is remote or virtual | 501 (until P9 and P10) |
| The caller may deploy nowhere in the repository | 401 (anonymous) or 403, before the body is read |
| The body is not `multipart/form-data` (as `pip search`'s XML-RPC is not) | 415 |
| `:action` is not `file_upload` (`submit`, `setup.py register`, is "neither required nor supported", R28 5) | 400 |
| No `content` part with a file name | 400 |
| `sha256_digest` or `blake2_256_digest` (hexadecimal) or `md5_digest` (hexadecimal, or URL-safe base64 without padding) does not match the content | 400 |
| The file name is not a distribution type above, or the content yields no `Name` and `Version` | 400 |
| The form's `name` (normalised) or `version` (PEP 440) disagrees with the content | 400 |
| The canonical path is under `packages/` or `simple/` | 400 |
| No Deploy on the canonical path | 401 or 403 |
| The generic deploy policy (decision 0032), then the enforcement settings | Their statuses (403 for the settings) |
| A file with other content is at the canonical path and the caller lacks Delete | 403 `Not enough permissions to delete/overwrite artifact '<repo>:<path>' (user: '<user>' needs DELETE permission).` |
| Otherwise | 200, empty body |

- The file is stored at the canonical path computed from its content, so `Inspect` runs once
  and the form's metadata, which uv sends as written and twine with its own spelling of the
  name (R28 5), never decides where a file goes. Only `name`, `version` and the digests are
  read from the form.
- **Re-uploads.** The same content at the canonical path is stored again with Deploy alone,
  as a REST deploy that declares its SHA-256 is (decision 0004): twine sends `sha256_digest`,
  so a re-run of the same build passes without `--skip-existing`. Other content replaces the
  file with Delete, or answers 7.x's 403 without it (RTFACT-26398), which Poetry's
  `--skip-existing`, and twine's up to 6.1, take for an existing file. Twine 6.2 removed
  that compatibility (R28 5); the pinned Twine 7.0.0 refuses `--skip-existing`
  for private repository URLs before sending an upload (`UnsupportedConfiguration`;
  [client source](https://twine.readthedocs.io/en/stable/_modules/twine/settings.html)).
  Acceptance checks prove this client restriction separately from successful ordinary
  same-content retries and both permission outcomes for changed bytes.
- **Digest mismatch** answers 400, as PyPI does. The upload is refused before anything is
  stored at the path. Whether 7.x checks the digests is inferred [I].
- `gpg_signature`, `attestations` and `comment` are ignored, as 7.x makes nothing of a
  signature (RTFACT-15972): no `.asc` is stored and no `data-gpg-sig` is written.
- The status codes for a malformed request are 400 and 415 rather than 5xx because twine
  retries a 5xx five times (R28 5). The messages are inferred [I].

### The JSON API

`GET /api/pypi/<repo>/pypi/<name>/json` and `.../<name>/<version>/json`, `application/json`,
built from the index (#540). `<name>` is matched normalised and `<version>` in its PEP 440 form,
without a redirect.

- **Which version** `/json` describes: the highest version, by PEP 440, that is neither a
  pre-release nor a development release and has a file that is not yanked; failing that, the
  highest version (RTFACT-30744, RTFACT-22366).
- **`info`**, from the metadata of the version's earliest-deployed file, as PyPI keeps the
  first upload's (R28 9): `author`, `author_email`, `classifiers`, `description`,
  `description_content_type`, `download_url`, `dynamic`, `home_page`, `keywords`, `license`,
  `license_expression`, `license_files`, `maintainer`, `maintainer_email`, `name`, `platform`,
  `project_urls` (an object), `provides_extra`, `requires_dist`, `requires_python`, `summary`,
  `version`, `yanked` and `yanked_reason`. The nine keys 7.111.4 left out are in, as from
  7.161.15. A field the metadata lacks is `null`.
- **`urls`**, one per readable file of the version: `comment_text` (`""`), `digests` (`md5`,
  `sha256`), `filename`, `md5_digest`, `packagetype` (`bdist_wheel`, `sdist` or `bdist_egg`),
  `python_version` (the wheel's Python tag, `source`, or the egg's), `requires_python`, `size`,
  `upload_time`, `upload_time_iso_8601`, `url` (absolute, from the base URL resolver), `yanked`
  and `yanked_reason`.
- **Left out:** `releases`, `vulnerabilities`, `bugtrack_url`, `info.downloads`, and
  `urls[].downloads` and `has_sig`, as 7.x leaves them out (7.111.4); and, inferred [I],
  `last_serial`, `docs_url`, `package_url`, `project_url` and `release_url`, which name
  PyPI's web pages, `digests.blake2b_256`, which is not stored, and `core-metadata`.
- **Unknown** project or version, or none readable: 404 in the Artifactory envelope.

### Reindex

`POST /api/pypi/<repo>/reindex[?async=…]` (#516, #540):
- **Manage** on the repository, as JFrog's reference requires (R28 10).
- **Which repositories:** PyPI local and federated. A missing repository answers 404, another
  package type and a remote or virtual repository 400 [I].
- **Queued** on the work queue (decision [0033](0033-persistent-work-queue.md)), keyed by
  repository. With `async` `true` or `1` it answers at once; without it, or with `false` or `0`,
  it waits for the queued run to finish, as 7.x's default is synchronous. Both answer 200
  `text/plain` `Recalculating index for pypi repository <repo> scheduled to run`, the reference's
  sample; a run that fails while a caller waits answers 500.
- **The rebuild** reads every file of the repository through `Inspect`, with its properties,
  and reconciles the index (`pkgindex.Reconcile`), so a reindex from an empty index reproduces
  it.

### Errors and other repositories

- **The envelope** of every error under `/api/pypi/` is Artifactory's,
  `{"errors":[{"status":…,"message":…}]}`, as every 7.x capture there is (R28 2, 3 and 9).
  `surfaceFor` picks it for `/artifactory/api/pypi/`, where research 10 had given plain
  text ([#532](https://github.com/weaveplatform/artifactweave/issues/532)).
- **Remote and virtual** PyPI repositories answer 501 in that envelope, naming the class, until
  P9 and P10 (decision 0032).

### Permissions

| Operation | Needs |
|---|---|
| Project list | Read; projects without a readable file are left out |
| Project page, JSON API | Read on a file; unreadable files are left out, and none readable is 404 |
| Download, `.metadata` | Read on the file (the wheel, for `.metadata`) |
| Upload | Deploy on the canonical path; Delete too to replace other content |
| `PUT` deploy | As the generic deploy |
| `pypi.yanked` and other properties | Annotate, through the property API |
| Reindex | Manage on the repository |

Anonymous callers get what anonymous access and the repository's permissions give them, as on
the other protocols.

## Rationale

**Index by metadata wherever the file is.** 7.x does: RTFACT-29892's query has no path
condition, and the documentation describes manual REST uploads, which land wherever the user
sends them. Artifactory users deploy wheels with `jf rt u` to folders of their own
(RTFACT-20305). A strict layout would hide those packages from
pip with no 7.x source behind it.

**The canonical folder from PEP 503.** 7.x's folder agrees with it for every name in lower case
without dots, and its rule for the rest is unknown. Taking it from the content rather than the
form gives one folder whichever client uploads, since twine and uv spell the name differently.

**Settings, not repository fields.** 7.x has no per-repository field for any of the four
(R28 12), and the Terraform provider sends none. A server-wide setting in `formats.Settings`
follows `npm.enforce_path` (decision 0034).

**PEP 658 behind a setting.** 7.x ships it off, behind a system property. Turning it on is one
setting, and uv falls back on `Range`, which every download supports, so the default costs pip
users only the wheel downloads it costs them on 7.x.

**Enforce layout literally.** JFrog's table refuses `jfrog_pypi-1.0.0.tar.gz` for a package
named `jfrog-pypi`, and its text calls the check strict. Normalising both sides would make the
setting a weaker check than the one users turned on. The duplicate row in JFrog's table that
refuses identical names is read as a mistake.

**The Artifactory envelope.** It is what 7.x answers on `/api/pypi/`. pip and twine show the
status line, uv shows the body as the error's text, and Poetry searches it for "overwrite
artifact"; none parses it, so nothing depends on plain text.

**No `.asc` and no `data-gpg-sig`.** 7.x stores no signature, PyPI ignores them, and twine
warns that it may stop sending them.

**Index at once.** JFrog intends an uploaded package to become installable; its quiet period
batches indexing work and is not the intent itself. Indexing in the upload's transaction meets
the intent sooner, so `pip install` right after `twine upload` finds the package, as CI
pipelines expect. Doing better than 7.x here is not a deviation (maintainer's rule,
2026-10-19).

**Alternatives considered:**
- *Strict layout, as npm's decision 0034:* off-canonical files would not be indexed, where 7.x
  indexes them.
- *PEP 658 always on:* faster resolution for pip, but a difference from 7.x's default for no
  client that needs it.
- *Folders as twine names them:* a uv upload of the same package would land elsewhere.
- *409 for a re-upload, to suit twine 7's `--skip-existing`:* 7.x answers 403 without Delete and
  replaces the file with it; the same content passing with Deploy alone already makes re-runs
  succeed. Twine 7 also refuses that option for private URLs before any HTTP call.
- *Storing index pages as files under `.pypi/`:* 6.x's `simple.html` broke on bad metadata
  (RTFACT-19510); pages computed from the index cannot drift from it.

## Artifactory 7.x check

The decision follows 7.161.32 and SaaS 7.174.0 ([research 28 section 16](../28-pypi.md#16-artifactory-7x-check)).
No self-managed release after 7.161.15 changes what a PyPI local repository answers; SaaS

## P9 shared retrieval contract

Remote implementation follows the [shared retrieval contract](../../implementation/remote-retrieval-contract.md)
(#613): metadata-only zap, cache aliases with no upstream traffic, bounded synchronous
refresh, typed source errors and transient no-store responses. Retain raw upstream
metadata independently of local indexes, rewrite only the client representation and
preserve signed bytes. Its adapter/field matrix assigns this format's P9 tickets and
P10/later handoffs. These are planned remote rules; the local behavior and current class
gates in this ADR remain unchanged until their implementation tickets land.

## Constraints

- **Projects named `packages` or `simple`** cannot be uploaded through the upload API.
- **Core metadata** is served for wheels only, and only with `pypi.core_metadata` on.
- **`upload-time` and `upload_time`** are the file's deploy time; a copy or a move gives the
  new item its own.
- **Two files of one name** at different paths are both listed, ordered by path; pip takes the
  first.
- **Unconfirmed:** what Artifactory answers for every item in research 28 section 15 is
  inferred, and on the live-comparison list (#216) for P19.

## Owned follow-up

P28 owns XML-RPC search for private local indexes and P10-backed virtual aggregation,
with permission-filtered results, bounded XML parsing and native search proof.
[JFrog still documents local/virtual search](https://docs.jfrog.com/artifactory/docs/pypi-repositories);
[pip distinguishes those indexes from PyPI.org](https://pip.pypa.io/en/latest/cli/pip_search/).
Public PyPI retiring XML-RPC is therefore not supersession of this capability.

The current upload parser ignores `attestations`, `gpg_signature` and `comment`.
P23/P28 must establish and implement the applicable signature/attestation and
provenance contracts; an ignored field is not proof of support. The target's refusal
of `submit/register` and Twine 7's client-side private-URL `--skip-existing` refusal
remain distinct compatibility/client facts, not missing server workflows.

The [capability roadmap](../../implementation/capability-roadmap.md) records the
phase boundaries under decision [0042](0042-capability-scope-and-supersession.md).
These assignments describe planned work, not current runtime support.
