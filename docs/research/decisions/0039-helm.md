# 0039: Helm and Helm OCI

Status: Proposed

Checked against: **Artifactory 7.161.32** (SaaS 7.174.0) on 2026-10-19 ([research 30 section 13](../30-helm.md#13-artifactory-7x-check), [#529](https://github.com/weaveplatform/artifactweave/issues/529)).

## Context

Helm reads a classic chart repository through one `index.yaml` and downloads the charts and
their `.prov` files at the URLs it names; Artifactory serves that at
`/artifactory/api/helm/<repo>/` and computes the index itself from the charts deployed with a
REST `PUT`. Helm 3.8 and later also push and pull charts as OCI artifacts, which Artifactory
serves through its Docker registry in `helmoci` repositories, and which P6 already serves
(decision [0031](0031-docker-oci-registry.md)). Decision [0032](0032-package-format-handlers.md)
gives formats their hooks, and decision [0033](0033-persistent-work-queue.md) the work queue.
[Research 30](../30-helm.md) holds the facts, cited below as R30.

This decision fixes what the Helm format indexes and derives, what `/api/helm/` answers, how
Enforce Layout and reindex behave, and what Helm OCI needs beyond P6. The first two parts
below, the per-repository `index.yaml` work and the `.prov` sidecar, are what the format
contract suite needs ([#533](https://github.com/weaveplatform/artifactweave/issues/533)).

## Decision

### Scope

- **`helm` local and federated repositories** get a Helm format, `internal/format/helm`, and
  the protocol `/artifactory/api/helm/{repoKey}/` mounted through the router kit of decision
  0032. Charts are deployed, copied, moved and deleted through the item routes, as on 7.x
  (R30 3).
- **`helm` remote and virtual repositories** answer 501 until P9 and P10 (decision 0032). What
  they will need is in R30 2.5; `_external` dependency rewriting is P9's.
- **`helmoci` repositories** stay with the Docker format and the registry (decision 0031), with
  the additions under "Helm OCI".

### `index.yaml` is per-repository derived work

- **One item per repository.** The kind is `helm.index`, keyed by the repository key alone. A
  repository has one `index.yaml` and every chart in it, in any folder, is an entry there
  (R30 2.2), so every write that changes the charts coalesces into the same item, whatever
  package it touched. Decision 0032 lists `index.yaml` among the kinds keyed by package; this
  decision keys it by repository, and #533 adds the per-repository option to the contract
  suite and to decision 0032.
- **Which writes queue it.** The hooks call `Env.Enqueue` in the write's own transaction (a
  copy or move runs the hooks of both repositories, so each queues its own):

  | Write | Queues `helm.index` |
  |---|---|
  | Deploy, checksum deploy or archive entry that stores a chart, or replaces one | yes |
  | Deploy that replaces a chart with a file that is not one | yes |
  | Deploy of any other file, a `.prov` included | no |
  | Delete of a chart, by any API (a build delete with its artifacts included) | yes |
  | Copy or move: the target when a chart lands there, the source when one leaves it | yes, each repository |
  | Trash restore of a chart | yes |
  | Property change on a chart | no: the index carries no property |
  | Full or partial reindex, once the package index is rebuilt | yes |
  | Client deploy or delete of the root `index.yaml` | yes |

  These are the writes JFrog's fixes say must regenerate the index: deploy and delete, the move
  source (RTFACT-30033), a second copy of the same chart (RTFACT-30758) and build deletes
  (RTFACT-30097, 7.84.10) (R30 2.4).
- **The run** reads the package index and each version's metadata (below) and the chart items'
  paths, SHA-256 and deploy times; it never opens an archive. It writes `index.yaml` at the
  repository root through `Derive`, as a derived item (`ClassDerived`) created and modified by
  `_system_`, so replication and federation skip it and each side recomputes it. It is
  idempotent.
- **Reads.** `Owed` names the repository's `helm.index` item for the root `index.yaml`, read
  through `/api/helm/` or the item route, so a read after a completed write never sees an
  index without it. A read finding no stored `index.yaml` and no item pending (a new repository,
  or one whose file a client deleted) enqueues the work and runs it with `EnsureFresh`. A parked
  item answers 500 in the protocol's envelope.
- **A client's root `index.yaml`** is stored with 201 and replaced by the next run, as Maven's
  artifact-level metadata is (decision [0036](0036-maven.md)): 7.x stores an uploaded index and
  its recalculation must drop what the charts do not back (RTFACT-18128, 7.12.3). An
  `index.yaml` in any other folder is an ordinary file.

### `.prov` is a sidecar the Helm format owns

- **What it is.** A file named `<chart path>.prov` beside a chart archive is that chart's
  provenance file (R30 3). Helm fetches it at the chart's URL plus `.prov`, so it is only
  useful at that path.
- **It is never a chart and never a version file.** It is stored as an ordinary file with its
  own checksums, is not linked to the chart's version in the package index, and is not named in
  `index.yaml`, which has no field for it. Neither Enforce Layout nor the index looks at it.
- **It follows its chart** through the operations that change where the chart is:
  - a delete of the chart deletes its `.prov` in the same operation, into the trash can when it
    is on;
  - a copy or move of the chart takes its `.prov` to the target's `<path>.prov`, under the same
    rules as the chart (an overwrite with other content needs Delete there); an operation that
    already names the `.prov`, such as a folder copy or a build promotion listing both, carries it
    once;
  - a trash restore of the chart restores the `.prov` the same delete removed.

  The caller needs the same permission on the `.prov` as on the chart; without it the chart's
  operation is refused, as for any path the caller may not change. A deploy that overwrites the
  chart leaves the `.prov` as it is, since the client usually uploads the new one next.
- **It may arrive first.** A `.prov` deployed where no chart is yet is stored, and becomes the
  chart's sidecar when the chart arrives. Deleting, copying or moving the `.prov` alone touches
  nothing else.
- **It is not a checksum sidecar.** `format.SidecarOwner` means that uploads named `.sha1` and
  the like are checksums of their file (decision 0032, Maven). Helm repositories do not take
  them so, and the Helm format does not implement it; #533 adds the owned sidecar as an option of
  its own, which Terraform's `_SHA256SUMS` and `.sig` files will also use.

### Charts and the package index

- **What is a chart.** A file anywhere in the repository whose name ends `.tgz` or `.tar.gz`, as
  6.20's `isHelmFile` reads it (R30 3), whose archive holds a `Chart.yaml` with a non-empty
  `name` and `version`:
  - the `Chart.yaml` directly inside the archive's single top-level folder, or, for a chart
    packed by hand, at the archive's root; never a subchart's under `charts/` (RTFACT-16103,
    RTFACT-17119);
  - read once by `Inspect`, outside the write's transaction, bounded as npm's tarball read is
    (decision [0034](0034-npm.md)); Windows line endings and any YAML string are accepted
    (RTFACT-21994, RTFACT-26006).

  Anything else, an unreadable or malformed archive included, is stored and not indexed, and
  the rest of the repository stays indexed (RTFACT-26509). A version that is not SemVer is still
  indexed when Enforce Layout does not refuse it, as 7.x indexes it (RTFACT-20334); Helm skips
  such an entry itself.
- **The package index** (decision [0018](0018-package-index.md)):
  - the package is the chart's `name`, per repository;
  - the version is `Chart.yaml`'s `version` as written;
  - its files are every chart archive with that name and version, which is more than one only
    without Enforce Layout's duplicate check;
  - the per-version metadata is the newest of those archives' `Chart.yaml`, kept as Helm's
    `Metadata` model reads it (unknown keys dropped), with that archive's path, SHA-256 and
    deploy time. "Newest" is the last deployed (`Modified`), as 7.x "retains only the latest
    entry and overwrites the URL" (R30 2.2). When it goes and another archive remains, the hook
    reads the remaining one's `Chart.yaml`;
  - order is `types.CompareSemver`, which `types.ComparatorFor(repo.Helm)` already returns.
- **Properties.** An indexed chart gets `chart.name`, `chart.version` and, when set,
  `chart.appVersion`, the keys of Artifactory's Helm package search (6.20
  `PackageSearchCriteria`; RTFACT-15566, 5.9.0); 7.x still writes `appVersion` as a property
  (RTFACT-26509). The format sets them, so they need no Annotate. They follow decision 0004: an
  overwrite with other content clears them, and the new chart's are set. That 7.161 uses these
  keys is **[I]**.

### The shape of `index.yaml`

- **Top level:** `apiVersion: v1`, `entries` and `generated` (the run's time), and nothing else:
  no `serverInfo`, `publicKeys` or `annotations`. An empty repository's index has `entries: {}`
  (RTFACT-21578).
- **Entries:** one list per chart name, newest first by Helm's own order (SemVer descending, a
  version that does not parse last; R30 2.1). One entry per name and version: the newest
  archive's.
- **Each entry** has the `Chart.yaml` fields Helm's model defines and the chart sets (`name`,
  `home`, `sources`, `version`, `description`, `keywords`, `maintainers`, `icon`, `apiVersion`,
  defaulting to `v1` when absent, `condition`, `tags`, `appVersion`, `deprecated`,
  `annotations`, `kubeVersion`, `dependencies`, `type`), then:
  - `urls`: one URL (below);
  - `created`: the archive's deploy time, RFC 3339 in UTC with milliseconds, as JFrog's capture
    shows it (R30 2.2), so a reindex gives the same value;
  - `digest`: the archive's SHA-256 in hex.
- **Only keys Helm knows.** Helm reads the index strictly, so a key outside its model would make
  the whole file unreadable (R30 1.1); `Chart.yaml` keys outside the model are dropped.
- **Dependencies keep `alias`.** 7.x strips it (RTFACT-30329), which Helm's source calls out;
  every `Dependency` field is kept, as Helm's own `helm repo index` keeps it. This follows the
  index Helm defines rather than that bug.
- **Quoting.** `version` and `appVersion` are always double-quoted, as 7.x quotes them from
  7.10.5 (RTFACT-20334); every other string is written so that a YAML reader reads it back as
  the same string, which the bugs in R30 2.2 show 7.x had to learn value by value. Keys are
  written in alphabetical order, as both Helm and 7.x write them.

### URLs in `index.yaml`

- **Stored form.** The derived file holds each chart's path from the repository root as a
  relative URL, each segment percent-encoded where a URL needs it. 7.x's stored file named
  charts `local://<path>`, which no client can follow (R30 2.2); whether 7.161 still does is
  **[I]** (#216).
- **Served form.** `GET /api/helm/<repo>/index.yaml` serves:
  - the relative URLs as stored when `helm.relative_urls` is on, the default, as every 7.x
    release after 2024-11-01 does (R30 2.3). Helm resolves them against the repository URL, so
    charts are fetched from `/artifactory/api/helm/<repo>/<path>` with the repository's
    credentials;
  - absolute URLs `<base>/artifactory/<repo>/<path>` when it is off, the form JFrog's captures
    show (R30 2.3), with `<base>`, the scheme and host before `/artifactory`, from the base URL
    resolver (`internal/server/baseurl`: `X-JFrog-Override-Base-Url`, then
    the configured base URL, then the forwarded headers, then the request), which is what
    RTFACT-27528 asks of 7.x for federated repositories.
- **The item route** (`GET /artifactory/<repo>/index.yaml`) serves the stored file, so
  `helm repo add <base>/artifactory/<repo>` works too.
- **Content-Type:** `application/x-yaml` on the `/api/helm/` route **[I]**; Helm reads only the
  status (R30 1.1).

### Routes under `/artifactory/api/helm/{repoKey}/`

| Request | Answer |
|---|---|
| `GET`, `HEAD index.yaml` (the root only) | The index, refreshed as under "Reads" |
| `GET`, `HEAD <path>` | The item at `<path>` through `ServeItem`: charts, `.prov` files and any other file, with download counts and the redirect policy of decision [0029](0029-cdn-delivery-and-download-redirect.md) |
| `POST reindex` | Full reindex (below), a generated operation beside the protocol |
| `POST <path>/reindex` | Partial reindex (below), a generated operation that #536 adds to the OpenAPI sources |
| Any other method on any path (`PUT`, `DELETE`, and `POST` but to `reindex`) | 405, `helm cm-push`'s `POST .../api/charts` included **[I]** (R30 1.4); deploys go to the item routes |

Errors use the Artifactory envelope, as the item routes' and every other route's under
`/artifactory/api/` do outside the registries with envelopes of their own (amended
2026-10-20, [#532](https://github.com/weaveplatform/artifactweave/issues/532); research 10 had
given Helm plain text). Helm reads only the status (R30 1.1), so nothing depends on the body.
No 7.x capture shows an error under `/api/helm/`; a Helm repository's `index.yaml` answered a
404 in the Artifactory envelope on 6.20 (RTFACT-22019), and 7.x's body is **[I]**. A
repository of another package type, or a missing one, answers as the router kit answers for
every protocol; 7.x's answer is **[I]**.

### Enforce Layout

- **Fields.** `forceNonDuplicateChart` and `forceMetadataNameVersion`, `false` by default, on
  local and federated `helm` repositories; 7.x enforces them on federated repositories from SaaS
  7.131.0 and self-managed 7.133.3 (RTDEV-66745, R30 4).
- **What is checked.** `Admit` checks every write that lands a chart-named file (`.tgz` or
  `.tar.gz`): a deploy, a checksum deploy, an archive entry, and the target of a copy or move,
  which is refused for that item and reported, as 7.x's documentation warns a copy or move into
  an enforcing repository may be (R30 4). A `.prov` and every other file pass.
- **The checks and their 403 messages**, in this order **[I]**:
  1. with `forceMetadataNameVersion`, a `Chart.yaml` that cannot be read or lacks a name or
     version: `This action is prevented due to the Enforce Layout Policy, the metadata of the
     package <file> could not be read or is malformed.`, where `<file>` is the file name
     without its extension;
  2. with `forceMetadataNameVersion`, a version that is not SemVer 2.0.0 (strict: no leading
     `v`, three numbers): `This action is prevented due to the Enforce Layout Policy, the
     specified package version <name>-<version> does not comply with the Semantic Versioning
     format.`;
  3. with `forceMetadataNameVersion`, a file name other than `<name>-<version>` with its
     extension: `This action is prevented due to the Enforce Layout Policy, the package file
     <file> does not match the package name/version <name>:<version> in the metadata file.`,
     with `<file>` as in 1. JFrog's example prints `chart-1.0.` for `chart-1.0.0.tgz`; the full
     name is used, and the example is on #216;
  4. with `forceNonDuplicateChart`, another chart archive at another path of the repository with
     the same `Chart.yaml` name and version: `This action is prevented due to the Enforce Layout
     Policy, a package with the same name and version <name>-<version> already exists in the
     repository.` A write to the same path is an overwrite, not a duplicate.

  The messages are 7.x's (R30 4) and answer in the envelope of the route that carried the
  write, the Artifactory envelope for the item routes.
- **Without the fields** every chart is stored, a duplicate name and version is indexed and the
  newest wins in `index.yaml`, as 7.x does (R30 2.2).
- **Set only at creation.** 7.x sets enforcement "only upon repository creation", and the
  Terraform provider refuses a change in the plan (R30 4, 7). A create may set either field. An
  update through the repositories API, the batch update or the configuration descriptor that
  gives either field a value other than the stored one answers 400 `The field
  '<field>' of a Helm repository can be set only when the repository is created`; one that
  omits it or repeats the stored value passes. What 7.x answers is **[I]**; refusing is chosen
  over keeping the stored value silently, so a caller never reads a success for a change that
  did not happen.
- **The global switch** (Packages Settings, the descriptor's
  `repositoriesGeneralConfig.helm.forceNonDuplicateChart` and `forceMetadataNameVersion`) is not
  offered: nothing applies the `repositoriesGeneralConfig` section (DV-084 refuses it), and the
  per-repository fields give the same enforcement repository by repository. That is a
  deliberate departure, which #548 registers, either by widening DV-084 or in its own range.

### Reindex

- **Full:** `POST /api/helm/<repo>/reindex` needs Manage on the repository, as 7.x requires "the
  set of permissions assumed by Manage" (R30 5) and as npm's reindex does (#516). It acts on
  local and federated `helm` repositories: another class or type answers 400 and a missing
  repository 404. It queues a rebuild of the repository's package index from every chart archive
  on the work queue, keyed by repository, and answers 200 in plain text,
  `Recalculating index for repository <repo> scheduled to run`, the words 7.x's UI shows
  (RTFACT-27188) **[I]** for the REST body. The rebuild reads each archive again, outside any
  long transaction, sets the properties, and then queues `helm.index`. It is a maintenance item,
  so no read waits for it (decision 0033).
- **Partial:** `POST /api/helm/<repo>/<path>/reindex` (SaaS 7.105.2, self-managed 7.111.4) needs
  the same permission and does the same for the charts under `<path>`, a folder read recursively
  or one archive. It is keyed by repository and path, so two partial reindexes of different paths
  never coalesce into one payload, and a pending full reindex covers them. A path with nothing at
  it answers 404 **[I]**.
- The shared reindex path is #516's; this decision fixes Helm's permission, timing and keys.

### Helm OCI

P6 already serves Helm OCI: a chart's manifest is an OCI image manifest whose config and layers
P6 accepts, the tag is the chart version with `+` written `_` by Helm, and the tags list,
referrers, Strict Tag Overwrite (DV-035), promotion, download redirects and `maxUniqueTags` and
`dockerTagRetention` all apply to `helmoci` (R30 6.3). What charts add:

- **Helm 3.18's digest twin.** Helm 3.18 and later, Helm 4 included, push each chart by digest
  and then by tag, so a push leaves `<chart>/sha256:<hex>/` beside `<chart>/<version>/` with the
  same manifest (R30 6.2). Max Unique Tags already counts tags only, which is what JFrog intends
  ("the human-readable tags used for consumption", known issue RTDEV-88173). The twin must not
  outlive the tag the limits remove, or the repository keeps every chart they removed:
  - a digest folder whose manifest a tag folder of the same image also holds is that tag's twin;
  - when Max Unique Tags removes a tag, its twin goes with it, as the tag's retained versions
    already do;
  - when a push replaces the tag's manifest under Tag Retention of 2 or more, the previous
    manifest's twin becomes the tag's retained version (its `docker.manifest` then names the
    tag), since it is the folder the retained copy would move to; retention then counts and
    trims it like any retained version. Under Tag Retention of 1 the twin stays, as any manifest
    pushed by digest does;
  - a twin that a list names, or that another tag of the image still holds, stays;
  - a client's own delete of a tag removes only the tag, as decision 0031 has it.

  This applies to Docker and OCI repositories too, since the registry cannot tell which client
  pushed. What 7.x's limits do with the twin is **[I]** (#216).
- **The chart's own version in the index.** A tag folder stays the version, so retention and the
  tags list are unchanged. When the config's media type is
  `application/vnd.cncf.helm.config.v1+json`, the version's metadata records the config's
  `name`, `version` (with its `+`) and `appVersion`, which a package API can show as 7.x's
  Packages view does (RTFACT-31105). No property is added to the manifest, since none is known
  for 7.x **[I]**.
- **`jf helm push`** works on the P6 layout: its AQL path search finds `manifest.json` and the
  `sha256__` blobs in `<sub>/<chart>/<version>/`, its recursive property edit sets `build.name`,
  `build.number` and `build.timestamp` on that folder, and the build-info module is of type
  `helm` (R30 1.3). A chart version holding `+` is not found by it, because it searches the
  version as written and the tag holds `_`; that is the client's fault, it fails the same way on
  7.x **[I]**, and the acceptance scenarios use versions without `+`.
- **Repository fields.** `artifactory_local_helmoci_repository` sends `maxUniqueTags` and
  `dockerTagRetention` on every create and update (R30 7); `pkg/repo` already keeps both for
  `helmoci`.

### Permissions

| Operation | Needs |
|---|---|
| `GET`, `HEAD /api/helm/<repo>/index.yaml` | Read on any path of the repository; the whole index is returned (below). No Read anywhere answers 401 to an anonymous caller and 403 otherwise |
| `GET`, `HEAD /artifactory/<repo>/index.yaml` | Read on `index.yaml`, as any item |
| Chart, `.prov` or other file through `/api/helm/` or the item route | Read on its path |
| Deploy a chart or `.prov` | Deploy on the path; Delete too to replace other content (decision 0004) |
| Delete a chart | Delete on the chart and on its `.prov` |
| Copy or move a chart | As the item API: Read on the source, Deploy on the target, Delete on the source for a move; the same on the `.prov` |
| Full and partial reindex | Manage on the repository |
| Helm OCI | As decision 0031 |

The index lists every chart in the repository to a caller who may read any of it, as JFrog
documents for repository metadata: "Any user with read access to a repository can view its
metadata, which includes the list of package, image, or artifact names it holds. This includes
users whose access is scoped to a specific path" ([docker-repositories](https://docs.jfrog.com/artifactory/docs/docker-repositories.md),
"Repository Metadata and Permissions"). Downloading a chart still needs Read on it. Whether a 7.x
local repository's index follows that rule is **[I]**; its virtual repositories filter by member
repository (RTFACT-25936), which P10 keeps.

### Configuration

`helm.relative_urls`, a `formats.Settings` key in a struct of its own in
`internal/config/helm.go`, environment variable `ARTIFACTWEAVE_HELM_RELATIVE_URLS`, default on:
on, `/api/helm/` serves relative chart URLs; off, absolute ones (above). It is Artifactory's
global `artifactory.helm.relative.urls.enabled`, which is on for every 7.x release after
2024-11-01. Unlike 7.x's flag, which "will only apply to new chart deployments" until a reindex,
it applies to every entry at once, since the stored file holds paths and the form is chosen when
the index is served.

## Rationale

- **One index item per repository.** 7.x keeps one `index.yaml` per repository and indexes every
  chart in it (R30 2.2), so per-package items would each rewrite the same file and race on it. One
  coalescing item turns a burst of deploys into one rebuild, which is what 7.x's event-based
  incremental indexing (7.33.6) aims at, without its failure modes: lost events with node events
  off (RTFACT-26812) or under an expired lock lease (RTDEV-48582), and a corrupt entry poisoning
  every later run (RTFACT-26509). The index is derived from the package index alone, so a rebuild
  never decompresses archives, and a reindex, a replica or a federation member reaches the same
  file.
- **Rebuild on read.** As for Maven metadata (decision 0036), the write path stays short and a
  client never reads an index that lags a completed deploy.
- **Paths in the stored file.** An absolute URL depends on the request (the override header, the
  forwarded host) and on the setting, so it cannot be stored once for every reader. A path can, and
  serving it as 7.x serves relative URLs today makes the default the cheap case. Helm sends the
  repository's credentials only to its own host (R30 1.1), so relative URLs also keep private
  charts downloadable behind a proxy that changes the host.
- **Strict keys and `alias`.** Helm reads the index strictly and validates each entry, and the
  bugs 7.x fixed one value at a time (R30 2.2) all came from writing YAML that did not read back
  as written. An index that holds exactly Helm's model and a real YAML encoder avoid that class of
  fault; keeping `alias` follows Helm's model where 7.x's known stripping does not.
- **The `.prov` sidecar.** Helm finds a provenance file only at its chart's URL plus `.prov` and
  checks it against the chart's digest. A chart moved without it fails `helm install --verify`,
  and one left behind after its chart is deleted would fail the check of the next chart deployed
  at that path. 7.x documents nothing either way (R30 3); following the chart is what Helm's
  layout needs, and it is on #216 so that P19 can register a deviation if 7.x leaves the file
  behind.
- **Enforce Layout fields set only at creation, refused on change.** 7.x's documentation, its
  release notes and the provider agree that the fields cannot change after creation. A 400 tells
  every client so, where silently keeping the stored value would report success for a change
  that did not happen; the provider never sends a change, so Terraform is unaffected.
- **The metadata rule for the index.** JFrog documents that repository metadata is visible to
  anyone who can read the repository, and the stored index is one file; filtering it per caller
  would cost a parse per request for a protection 7.x does not document for local repositories.
  Teams that must not see each other's chart names use separate repositories behind a virtual
  one, as JFrog advises.
- **The digest twin.** Max Unique Tags and Tag Retention exist to bound what an image keeps;
  Helm's second push would otherwise leave one manifest per pushed version forever, and 7.x's own
  retention removes "nested images, layers, and blobs" with a tag from 7.75.3 (R30 6.2). Removing
  the twin with the tag Max Unique Tags removes keeps N tags and nothing more, which is JFrog's
  stated intent in RTDEV-88173, and counting it as the retained version under Tag Retention keeps
  that limit honest too.

## Artifactory 7.x check

The decision stands against 7.161.32 and SaaS 7.174.0 ([research 30 section 13](../30-helm.md#13-artifactory-7x-check)):
- **Relative URLs by default** (deprecations in process, 2024-11-01), and the setting that turns
  them off.
- **Regeneration on move, copy and build delete** (RTFACT-30033, RTFACT-30758, RTFACT-30097 and
  7.84.10), which the queueing table covers.
- **Enforce Layout** (SaaS 7.104.2, self-managed 7.104.5): two per-repository fields set at
  creation, four 403 messages, federated repositories from 7.131.0 and 7.133.3; the global switch
  is not offered.
- **Partial reindex** (SaaS 7.105.2, self-managed 7.111.4), with Manage, as the archived REST
  reference requires.
- **Helm OCI:** Strict Tag Overwrite (7.146.7), retention fields, cleanup's view of Helm 3.18's
  two nodes (known issue RTDEV-88173), download redirects (7.146.12); nothing else changes the
  registry.
- **Following intent over bugs:** 7.x strips dependency aliases (RTFACT-30329), wrote
  `local://` URLs a local repository's clients could not follow (RTFACT-27527, RTFACT-27528) and
  adds quotes it should not (known issue RTDEV-27263); artifactweave writes the index Helm
  defines instead. None is a deviation: each is a 7.x fault, not its intended behaviour.

## Constraints

- The **[I]** points of research 30 section 11 are open until the live comparison (P19,
  [#216](https://github.com/weaveplatform/artifactweave/issues/216)). The stored form of the
  index, the `.prov` sidecar, the answer to an update of the enforce fields, the property keys,
  the reindex body and the digest twin are the ones that could change this decision.
- The global Enforce Layout switch is a departure #548 registers.
- `helm cm-push` cannot publish to artifactweave, as to 7.x: charts are deployed with a REST
  `PUT` or pushed to a Helm OCI repository.
- Helm clients below 3.0.0 are not supported, as on 7.x; relative URLs need Helm 3.
