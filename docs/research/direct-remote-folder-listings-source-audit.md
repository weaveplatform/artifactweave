# Direct remote folder listing source audit

Audited 2026-11-18 for #1640. **[S] OSS 7.161.26 confirms the direct HTML folder path includes remote resources, merges cache children first, and preserves an existing cached folder after upstream listing I/O failure. Two issue assumptions exceed this evidence: same-name cached entries retain their type, and unexpected exceptions inside the HTML service become 404, not 500.**

Labels: **[D]** current first-party documentation/release evidence; **[S]** verified 7.161.26 source/control flow, without a live response capture; **[I]** inference, internal contract, or unresolved current-version behavior.

## Union, existence, filtering, ownership

[S] `R/service/RepositoryBrowsingServiceImpl.java:262–305` enables upstream resources only when criteria, `isListRemoteFolderItems`, and parent-path acceptance permit. With local storage enabled, it browses `<remote>-cache` first. Only `ItemNotFoundRuntimeException` is caught; absent cache is tolerable only when upstream listing is enabled. A successful empty cache browse still sets `pathExistsInCache=true` (291).

[S] Empty cached folders therefore survive empty/failed upstream listings: local browsing returns empty normally at **191–194**; upstream emptiness throws only when cache presence is false at **308–317**. A missing arbitrary subfolder is not an existing empty folder (`T/ItemTree.java:79–92`). Repository root is distinct: `R/RemoteRepoBase.java:258–266` initializes the cache; `R/db/DbLocalRepo.java:142–145` delegates to the mixin, whose stored root is created/validated by `R/db/DbStoringRepoMixin.java:201,227–231`. A normally initialized store-local remote can have root presence before any artifact download. With storage disabled and upstream listing disabled, the remote method returns its initial empty list; this is not a cache-presence proof.

[S] The presence flag records successful browsing, not an unconditional physical-existence check: `RepositoryBrowsingServiceImpl.java:172–177` can return empty for rejected/blackout paths before item lookup, under `native.browser.return.empty.when.non.accessible` (default true, `ConstantValues.java:1234`). Keep this default-empty behavior separate from a readable, accepted, physically present empty folder.

[S] Cache browsing applies Read and include/exclude filters (`RepositoryBrowsingServiceImpl.java:172–181`; `T/TreeBrowsingCriteriaBuilder.java:89–95,107–110,126–129`). Upstream additions require Read at the cache path and remote pattern acceptance (`RepositoryBrowsingServiceImpl.java:236–238,323–338`). Cache config copies remote base/security configuration (`base/config/src/main/java/org/artifactory/model/LocalCacheRepoConfig.java:38–49`). Offline, assumed-offline, blackout, or the setting being off disable upstream listing (`RemoteRepoBase.java:361–390`), leaving the cache path and its normal errors.

[S] **Cache wins a same-name conflict**, including its folder/file type and metadata: `RepositoryBrowsingServiceImpl.java:320–335,819–835` snapshots cached names and excludes matching upstream names; it never promotes a cached file to a folder. Cached item ownership stays the cache path (`A/BrowsableItem.java:60–67`), while remote-only items use the remote path (`RepositoryBrowsingServiceImpl.java:325–330`). HTML links are relative names and add `/` only for the selected item's type (`BrowseNativeHtmlService.java:194–209`). Upstream duplicates are not universally deduplicated: the names set is never extended and `R/remote/browse/HtmlRepositoryBrowser.java:58–79` collects matching anchors into a list. **[I] “Folder if either side” and universal one-row-per-name normalization are broader internal choices, not established vendor behavior.**

## Error phases and retained uncertainty

[S] `RemoteRepoBase.java:1608–1647` uses listing/missed caches and catches **`IOException` from `getChildUrls`**, returning empty. Non-200 upstream responses and size-limit failures take this route (`R/remote/browse/RemoteRepositoryBrowser.java:57–81`; `base/common/src/main/java/org/artifactory/request/RemoteRequestException.java:35`). With a readable cached folder this preserves its listing; without folder presence it triggers the not-found path. Valid canonical upstream entries removed by repository patterns can leave a successful empty listing; caller Read is distinct. `BaseBrowseNativeService.java:281–309` can challenge when `RootNodesFilterResult` finds every child denied by Read. Do not generalize pattern-only presence into a universal 200 for all Read-filtered cases. Runtime browser/configuration faults and faults outside that I/O catch can still abort a warm listing.

[S] Own SQL/configuration failures are different internally: root/child SQL errors become `VfsException` (`F/FileServiceImpl.java:152–154,405–418,466–475`), which the missing-item-only catches do not tolerate; they abort the partial list. Known configuration loader failures throw, while an optional cache-miss fallback catches exceptions and returns null (`R/cache/RepoConfigCache.java:576–600,629–651`). **Nevertheless `BrowseNativeHtmlService.java:79–81` catches all `Exception` within execution and selects 404. A blanket direct-folder own-storage 500 claim is contradicted by this source path.** Earlier routing/configuration failures outside that catch are not settled by it.

[S] The separate [metadata fault audit](virtual-metadata-faults-source-audit.md) concerns a download/interceptor path: member-content `IOException`/`StorageException` can be tolerated there, while initial lookup failures abort. Its download 500 mapping cannot be transferred to this HTML handler. No member artifact content is read by the folder union itself.

[I] The bounded implementation plan preserves earlier dispatch, typed Source.Read/current-authority and ended-context mappings; an existing own-source lookup 500 is a retained project answer, not proven vendor HTML behavior. Newly introduced cached-folder Get/Children composition exceptions instead abort the direct HTML list with sanitized 404, following the inspected execute catch. The Java catch contradicts a general 500 claim inside its getItems chain. Exact text and current closed 7.x wire behavior remain unobserved. Keep proposed #216 comparisons local for explicit review; this audit made no public writes.
