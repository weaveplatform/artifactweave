# Phase 9c Git LFS file locking research

Research baseline: **2026-10-26**. Owner: [AUT-08 #843](https://github.com/weaveplatform/artifactweave/issues/843), following core Git LFS [#787](https://github.com/weaveplatform/artifactweave/issues/787). Claims below are **documented** (D), **observed in artifactweave source** (S), or an **implementation inference** (I). No live Artifactory lock request/response capture was available; JFrog-specific parity details belong to [#216](https://github.com/weaveplatform/artifactweave/issues/216).

## Client and wire contract

**D:** JFrog's configured LFS server URL is `/artifactory/api/lfs/{repoKey}`. The [Git LFS File Locking API](https://github.com/git-lfs/git-lfs/blob/main/docs/api/locking.md) appends these paths to that URL. Every locking request sends `Accept` and `Content-Type: application/vnd.git-lfs+json`; `Content-Type` may add `charset=utf-8`. Successful and specified error responses use the same media type. Optional `ref.name` is a fully qualified ref for authorization, **not** a branch-specific lock namespace in this version. [JFrog Git LFS guide](https://docs.jfrog.com/artifactory/docs/git-lfs-repositories), [Git LFS locking specification](https://github.com/git-lfs/git-lfs/blob/main/docs/api/locking.md).

| Route | Documented request | Documented response and access |
|---|---|---|
| `POST /locks` | JSON `path` relative to Git worktree root; optional `ref: {"name":"refs/heads/main"}`. | `201 {"lock": {...}}`; existing path `409` with conflicting `lock` and `message`; no push access `403`. Lock fields: string `id`, relative `path`, uppercase RFC 3339 `locked_at` at second precision, optional `owner.name` from authenticated creator. [Spec](https://github.com/git-lfs/git-lfs/blob/main/docs/api/locking.md#create-lock). |
| `GET /locks` | Query `path`, `id`, `cursor`, `limit`, `refspec`; bounded limit. | `200 {"locks":[], "next_cursor": "..."}` (cursor only when more); no pull access `403`. Empty result must contain `[]`. [Spec](https://github.com/git-lfs/git-lfs/blob/main/docs/api/locking.md#list-locks). |
| `POST /locks/verify` | JSON optional `cursor`, `limit`, `ref`. | `200 {"ours":[], "theirs":[], "next_cursor": "..."}`; no push access `403`. Other users' matching path locks in `theirs` can halt the Git LFS pre-push check. A `404` means locking is unimplemented and **does not** halt pushes, so it cannot stand in for authorization or upstream failure. [Spec](https://github.com/git-lfs/git-lfs/blob/main/docs/api/locking.md#list-locks-for-verification). |
| `POST /locks/{id}/unlock` | JSON optional `force: true` and `ref`. | `200 {"lock": {...}}` with removed lock; no push access or non-owner without force `403`. The spec allows force for another user's lock, while JFrog says host/project policy controls who may force-unlock. [Spec](https://github.com/git-lfs/git-lfs/blob/main/docs/api/locking.md#delete-lock), [JFrog guide](https://docs.jfrog.com/artifactory/docs/git-lfs-repositories). |

**D:** The spec's errors contain `message` and may contain `request_id` and `documentation_url`; it does not define every validation or missing-ID status. JFrog documents `git lfs lock`, `locks`, `locks --verify`, and `unlock` but publishes no Artifactory-specific lock wire examples. [Git LFS locking specification](https://github.com/git-lfs/git-lfs/blob/main/docs/api/locking.md), [JFrog guide](https://docs.jfrog.com/artifactory/docs/git-lfs-repositories).

## Ownership, permission and conflict boundary

- **D:** A lock reserves a worktree **path** across the repository; the v1 `ref` is only an authorization input. Create/verify/unlock require push access; list requires pull access. Verification partitions all visible locks by authenticated owner. [Git LFS locking specification](https://github.com/git-lfs/git-lfs/blob/main/docs/api/locking.md).
- **D:** JFrog calls locking cooperative, with server-stored identity-bound locks; host/project policy determines force-unlock and whether Git pushes are blocked. The Git LFS pre-push hook uses `locks/verify` to detect paths locked by others. The LFS batch/basic object protocol carries only SHA-256 OID and size, with no worktree path. Consequently an artifactweave raw object PUT cannot truthfully reject a conflicting **file** lock from its OID alone; claim conflict enforcement through verification/native Git client, not through inferred OID-to-path metadata. [JFrog guide](https://docs.jfrog.com/artifactory/docs/git-lfs-repositories), [Git LFS locking specification](https://github.com/git-lfs/git-lfs/blob/main/docs/api/locking.md), [Git LFS batch specification](https://github.com/git-lfs/git-lfs/blob/main/docs/api/batch.md).
- **S:** `auth.RequireAuthenticated` exposes the server-verified principal, and `pkgroute.Kit.Can` checks `READ`, `WRITE`, or `DELETE` on a path in the resolved repository. The existing Terraform backend uses `DELETE` on its workspace path for force-unlock; `MANAGE` primarily controls permission grants. [Principal](../../internal/auth/principal.go), [permission kit](../../internal/server/pkgroute/pkgroute.go), [actions](../../pkg/types/permission.go), [Terraform backend decision](decisions/0041-terraform-backend.md), [authorization decision](decisions/0006-authorization-native-permission-model.md).
- **I:** Persist owner identity from `Principal.Name` (never client JSON). Map pull/push to `ActionRead`/`ActionWrite` on the validated worktree-relative lock path; require `ActionDelete` **in addition to write** when force-unlocking another owner's lock. The extra write check follows Git LFS's push requirement and Delete follows the repo's existing force-unlock precedent. This is an artifactweave policy, not a documented JFrog action mapping. L/F/R checks use their repository grant; V checks resolved readable members for list/verify and the configured deployment member for mutations. Virtual keys cannot be permission targets in the local permission API, so no grant on the V key is required. A lock path is a Git path, while object permissions use `objects/{oid}`; repo-level grants should be included in proof, and fine-grained path grants need explicit tests rather than an assumed OID mapping. [Permission kit](../../internal/server/pkgroute/pkgroute.go), [authorization decision](decisions/0006-authorization-native-permission-model.md), [Terraform backend decision](decisions/0041-terraform-backend.md), [JFrog guide](https://docs.jfrog.com/artifactory/docs/git-lfs-repositories).
- **I:** Reject empty/absolute/traversal/ambiguous paths and malformed/bounded refs before persistence; do not silently canonicalize two client paths to one other file. Validate media type, JSON body size, unknown shape, ID and pagination inputs. Filter list and verify results by permission **before disclosure**. A conflict response may include the existing lock only if the caller may read that path; otherwise return a generic refusal, with no owner/path leak. These bounds implement #843's security requirements; the upstream spec does not prescribe a path validation algorithm. [#843](https://github.com/weaveplatform/artifactweave/issues/843), [Git LFS locking specification](https://github.com/git-lfs/git-lfs/blob/main/docs/api/locking.md).

## Durable state and repository classes

- **S:** The current [Git LFS handler](../../internal/server/gitlfs/protocol.go) registers only batch/basic object routes. Its `targetRequest` resolves virtual writes to the configured L/F deployment target and rejects direct remote writes; `members` preserves configured virtual order and authenticated member requests. [Protocol](../../internal/server/gitlfs/protocol.go).
- **S:** `store.Store` has no lock interface. It spans [in-memory](../../pkg/store/inmem/inmem.go), [SQLite](../../internal/sqlstore/sqlite/sqlite.go), and [PostgreSQL](../../internal/sqlstore/postgres/postgres.go), with [store contracts](../../pkg/store/storetest/core.go). SQLite uses immediate transactions and WAL; SQL migrations currently end at `0016_repository_header_secrets.sql`. [Store](../../pkg/store/store.go), [SQLite migrations](../../internal/sqlstore/sqlite/migrations), [PostgreSQL migrations](../../internal/sqlstore/postgres/migrations).
- **I:** Add a dedicated `LockStore` with atomic create/get/list/delete, unique `(repo_key, path)` plus unique opaque ID, authenticated owner, UTC creation time, and repository-delete cleanup. Implement it in all three backends and shared store contract tests. Use deterministic keyset pagination over `(locked_at, id)` or another stable unique order, bounded by the existing `store.Page` policy. Authorization-filter before filling a page; cursors should not expose other repositories or skip a caller's later visible locks. Store locks separately from object/blob/remote-cache rows so object delete, restore or reindex cannot rewrite lock ownership. [Store](../../pkg/store/store.go), [pagination](../../pkg/store/inmem/page.go), [#843](https://github.com/weaveplatform/artifactweave/issues/843).
- **I:** L and one-node F use their own durable lock namespace. A V create goes to its configured L/F deploy target after checking readable members for a duplicate path; V list follows configured member order and filters each member by caller permissions. V verify inspects the unified member view and fails closed if a relevant member cannot be checked, so it never reports an empty `theirs` merely because an earlier source failed. The caller needs write on the deployment member and read on each inspected member lock; a V-key permission grant is neither available nor required. Deduplicate a target appearing through multiple member paths. The public JFrog guide documents L/R/V repositories and a V deploy target for **blobs**, but does not define lock aggregation or target behavior, so these are artifactweave decisions pending a live capture. Cross-peer F lock convergence remains P13. [JFrog guide](https://docs.jfrog.com/artifactory/docs/git-lfs-repositories), [authorization decision](decisions/0006-authorization-native-permission-model.md), [protocol](../../internal/server/gitlfs/protocol.go), [#843](https://github.com/weaveplatform/artifactweave/issues/843).
- **D:** JFrog describes R as a caching proxy that cannot accept deployment of new artifacts. [Remote repository guide](https://docs.jfrog.com/artifactory/docs/remote-repositories). **S:** artifactweave's [source service](../../internal/source/source.go) currently admits only a closed, validated Git LFS **download** batch POST and guarded object GET; there is no lock-operation contract. **I:** Do not add an unguarded generic POST proxy. R create/unlock and push-oriented verify should explicitly refuse while R remains read-only, unless a captured JFrog contract establishes safe upstream mutation or push verification. R `GET /locks` needs a narrow, validated source-policy operation with upstream freshness and authorization; a fabricated empty local `200` would misstate upstream state. On offline/source failure, return a real error, never an empty success or `404`. This is the main unresolved design point for #843. [JFrog remote guide](https://docs.jfrog.com/artifactory/docs/remote-repositories), [source service](../../internal/source/source.go), [Git LFS locking specification](https://github.com/git-lfs/git-lfs/blob/main/docs/api/locking.md).

## Bounded implementation and proof

**I:** One #843 PR can add the four routes to `gitlfs.Protocol`, a small lock service atop the new durable store contract, and format-owned tests. The native acceptance image already pins Git LFS 3.8.1; extend its existing [fixture](../../test/acceptance/features/gitlfs.feature) with two authenticated users running real `git lfs lock`, `locks`, `locks --verify` and `unlock`. Prove L and F persistence across process restart, V deployment and ordered/member-safe results, duplicate path `409`, owner-only and Delete-authorized force unlock, pagination, denied/revoked/invalid input, and no state mutation on failed calls. For R, test the selected read/proxy policy and failure behavior with an upstream fixture; do not change client fixtures to accommodate server defects. Name new Go tests `TestUnit...` or `TestAcc...` and keep format ownership. [#843](https://github.com/weaveplatform/artifactweave/issues/843), [native fixture](../../test/acceptance/features/gitlfs.feature), [Git LFS locking specification](https://github.com/git-lfs/git-lfs/blob/main/docs/api/locking.md).

**Unverified JFrog parity:** precise force privilege, remote lock forwarding and caching, virtual aggregation/write target semantics, missing-ID/validation envelopes, and live response fields. Obtain a sanitized target capture in [#216](https://github.com/weaveplatform/artifactweave/issues/216); do not present the artifactweave inferences above as observed Artifactory behavior. [JFrog guide](https://docs.jfrog.com/artifactory/docs/git-lfs-repositories).
