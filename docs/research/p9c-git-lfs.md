# Phase 9c Git LFS native repository research

Research baseline: **2026-10-26**. Owner: [AUT-06 #787](https://github.com/weaveplatform/artifactweave/issues/787). Claims below are **documented** (D), **observed in artifactweave source** (S), or an **implementation inference** (I). No live Artifactory request capture was available; verify JFrog-specific transfer details against a target in P19 [#216](https://github.com/weaveplatform/artifactweave/issues/216).

## Client and repository contract

- **D:** JFrog configures Git LFS at `/artifactory/api/lfs/{repoKey}` using `lfs.url` in `.lfsconfig` or a remote-specific `lfsurl`. Its current guide describes local, remote and virtual repositories, remote proxying of another Artifactory LFS repository, and a virtual repository with a default deployment target for both reads and uploads. [JFrog Git LFS guide](https://docs.jfrog.com/artifactory/docs/git-lfs-repositories), [JFrog class table](https://docs.jfrog.com/artifactory/docs/repository-support-for-package-clients).
- **D:** The JFrog class table marks Git LFS L/R/V. **S:** artifactweave's approved [inventory](../implementation/package-format-matrix.md) and repository enums also register one-node F. The ticket requires native proof for L/R/V/F and leaves cross-peer convergence to P13. [Class table](https://docs.jfrog.com/artifactory/docs/repository-support-for-package-clients), [#787](https://github.com/weaveplatform/artifactweave/issues/787).
- **D:** JFrog stores bytes under `objects/{oid[0:2]}/{oid[2:4]}/{oid}`, using the client's SHA-256 OID. It says LFS blobs carry only OID and size, so metadata must not be invented from Git file names. [JFrog Git LFS guide](https://docs.jfrog.com/artifactory/docs/git-lfs-repositories).
- **D:** The Git LFS client's configured server URL is independent of its Git remote, and `git lfs env` reports the effective endpoint. A native fixture can use a local Git repository plus explicit `lfs.url`, push/fetch through artifactweave, and verify checked-out bytes. [Git LFS server discovery](https://github.com/git-lfs/git-lfs/blob/main/docs/api/server-discovery.md). Pin **Git LFS 3.8.1** for this cycle; its upstream release was published 2026-10-22. [Official releases](https://github.com/git-lfs/git-lfs/releases/tag/v3.8.1).

## Batch and object transfer

- **D:** `POST {lfsURL}/objects/batch` takes `application/vnd.git-lfs+json` (including optional `charset=utf-8`) and `operation: upload|download`, optional `transfers`, optional `ref.name`, and objects with OID and size. `sha256` is the default hash algorithm. The basic adapter is the interoperable baseline. A successful batch returns HTTP 200 with per-object actions or errors. A present download action is mandatory for an available object; a present upload action asks the client to transfer bytes, while no upload action tells it that the server already has the object. [Git LFS Batch API](https://github.com/git-lfs/git-lfs/blob/main/docs/api/batch.md).
- **D:** Basic transfer uses a GET action for raw download and a PUT action for raw upload, with action URLs and optional headers from batch. A server may also supply a POST verify action, which checks OID and size after upload. [Git LFS Basic Transfer API](https://github.com/git-lfs/git-lfs/blob/main/docs/api/basic-transfers.md).
- **I:** The core #787 PR should use repository-owned action URLs, bounded request/response parsing, SHA-256 and size verification **before** publishing a successful object, permission checks on both batch and transfer requests, and no cross-repository existence disclosure. A remote batch's upstream action URLs must be validated and fetched under P9 source policy rather than passed to the client as uncontrolled hosts. These controls follow the ticket's integrity and authorization acceptance and the existing source boundary, not a published JFrog wire capture. [#787](https://github.com/weaveplatform/artifactweave/issues/787), [remote retrieval contract](../implementation/remote-retrieval-contract.md).
- **S:** artifactweave's Hugging Face handler already parses an LFS upload batch and signs upload URLs, but it only accepts Hugging Face model uploads above its regular-file threshold and uses model-specific identity and layout. It is a security and API pattern, not the standalone `gitlfs` handler. The standalone protocol is absent and inventory still calls it a generic route. [Hugging Face protocol](../../internal/server/huggingface/protocol.go), [upload handler](../../internal/server/huggingface/upload.go), [inventory](../implementation/package-format-matrix.md).
- **S:** `pkgroute.Protocol` mounts `/artifactory/api/{name}/{repoKey}` and supplies class-specific sources; `source.Service` provides bounded/cache-aware remote reads including canonical POST metadata variants. Implement a `gitlfs` protocol and lifecycle handler through these seams, with explicit local/F, remote cache/offline, virtual ordered-member/deploy-target behavior. [router kit](../../internal/server/pkgroute/pkgroute.go), [source service](../../internal/source/source.go), [server registration](../../internal/server/server.go).

## Separate locking contract discovered in JFrog guide

**D:** JFrog also claims Git LFS file locking with `git lfs lock`, `unlock`, `locks`, and verification. The #787 body does not name these operations. [JFrog Git LFS guide](https://docs.jfrog.com/artifactory/docs/git-lfs-repositories), [#787](https://github.com/weaveplatform/artifactweave/issues/787). The upstream [Git LFS Locking API](https://github.com/git-lfs/git-lfs/blob/main/docs/api/locking.md) defines the following routes relative to `{lfsURL}`:

| Route | Required behavior |
|---|---|
| `POST /locks` | Push permission; exclusive normalized path; `201` with lock ID/path/time/owner; `409` and existing lock on collision; `403` on denied write. |
| `GET /locks` | Pull permission; filter by path/ID/refspec, bounded `limit` and `cursor`; `200` with `locks` (empty array if none) and optional `next_cursor`; `403` on denied read. |
| `POST /locks/verify` | Push permission; JSON `ref`, `limit`, `cursor`; `200` with paged `ours` and `theirs` arrays. The client uses `theirs` to stop a conflicting push. A `404` signals no locking implementation, so returning it indefinitely would misrepresent JFrog support. |
| `POST /locks/{id}/unlock` | Push permission; owner only unless permitted `force`; `200` with removed lock; `403` on denied write/ownership. |

**I:** This is a genuinely separate persistent, identity-bound feature, so create one P9c child issue depending on #787, with its own PR. The native-client acceptance should run `git lfs lock`, `locks`, `unlock`, and a conflicting-owner `locks/verify`/pre-push check against a repository with two authorized users. Server checks should cover duplicate path, cross-user visibility, force policy, pagination, malformed path/ref, permission revocation, and one-node F behavior. Virtual write must follow the configured deploy target; remote lock proxying requires a documented source-policy decision. The Git LFS API defines wire behavior, while JFrog's public guide does not publish its exact lock storage or remote/virtual lock semantics; any JFrog-specific parity claim remains inferred until captured. [Git LFS Locking API](https://github.com/git-lfs/git-lfs/blob/main/docs/api/locking.md), [JFrog Git LFS guide](https://docs.jfrog.com/artifactory/docs/git-lfs-repositories).

## Core PR proof and open questions

Implementation evidence on 2026-10-26: the pinned Git LFS 3.8.1 image passed
the four [native acceptance scenarios](../../test/acceptance/features/gitlfs.feature)
against the real server, including local and one-node federated publish/fresh
clone, virtual deploy target and ordered read, and remote cold/offline fetch
from two fresh clients. The client revealed an existing product middleware
defect: it changed `application/vnd.git-lfs+json; charset=utf-8` into
`application/json; charset=utf-8` before the protocol handler. The PR fixes
that behavior in [the middleware](../../internal/server/middleware.go) and
retains the original native client request. Locking remains [#843](https://github.com/weaveplatform/artifactweave/issues/843).

1. Pin the official Git LFS 3.8.1 client in a reproducible acceptance image; use unchanged tracked large-file bytes in a local Git fixture and point `.lfsconfig` at `/artifactory/api/lfs/{repoKey}`. Run real `git lfs push` and fetch/checkout through L, R, V and one-node F according to #787; verify SHA-256 of retrieved bytes. [Git LFS server discovery](https://github.com/git-lfs/git-lfs/blob/main/docs/api/server-discovery.md), [#787](https://github.com/weaveplatform/artifactweave/issues/787).
2. Exercise wrong OID/size, invalid media type/body, permission denial, missing object, changed upstream metadata, redirect/origin limits, remote offline cache, virtual member visibility, delete/restore/reindex. Count only native client or exact wire contract results; generic item CRUD is insufficient. [Batch API](https://github.com/git-lfs/git-lfs/blob/main/docs/api/batch.md), [#787](https://github.com/weaveplatform/artifactweave/issues/787).
3. The public JFrog guide does not specify whether transfer action URLs use `/artifactory/{repo}/objects/...` or another internal endpoint, nor exact error envelope for its lock API. Treat those as unverified Artifactory parity details for [#216](https://github.com/weaveplatform/artifactweave/issues/216); do not weaken Git LFS client behavior to a guess. [JFrog Git LFS guide](https://docs.jfrog.com/artifactory/docs/git-lfs-repositories).
