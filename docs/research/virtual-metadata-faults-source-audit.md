# Virtual Maven metadata fault compatibility audit

Audited 2026-11-18 for #1686. **OSS 7.161.26 deliberately tolerates member-content `IOException` and `StorageException` failures; promoting every local blob/read failure to 500 contradicts that source. Initial item lookup failures and known-configuration loader failures have a different, aborting path.** The distinction is the operation's phase, not simply local storage versus upstream.

## Version and evidence limits

The reused source is JFrog's **7.161.26 OSS** [source archive](https://releases.jfrog.io/artifactory/bintray-artifactory/org/artifactory/oss/jfrog-artifactory-oss/7.161.26/jfrog-artifactory-oss-7.161.26-sources.tar.gz), with [first-party artifact metadata](https://releases.jfrog.io/artifactory/api/storage/bintray-artifactory/org/artifactory/oss/jfrog-artifactory-oss/7.161.26/jfrog-artifactory-oss-7.161.26-sources.tar.gz) recording SHA-256 `b867422f3137c542b402c38a2ca2584396ef431b691ca70f038ff5cc3768802c` and publication on 2026-09-08. A fresh, small [public OSS directory listing](https://releases.jfrog.io/artifactory/api/storage/bintray-artifactory/org/artifactory/oss/jfrog-artifactory-oss/) still ends at 7.161.26 numerically. No additional source archive was downloaded.

This is not proof of settled current 7.x behavior. Current [self-managed release notes](https://docs.jfrog.com/releases/docs/artifactory-self-managed-releases) list **7.173.21, released 2026-11-17**, and say detailed fixes now require authentication. The current [Maven guide](https://docs.jfrog.com/artifactory/docs/maven-repositories#maven-metadata-in-virtual-repositories) describes aggregation and priority resolution but specifies no storage-fault status. Bounded searches of JFrog documentation, public release notes, and indexed JFrog issues found no newer primary evidence changing this exception policy. No Artifactory trial or live response capture was performed.

## What 7.161.26 actually does

All source references below are relative to the reused `.tools/p10-oss7/jfrog-artifactory-7.161.26/` tree; paths and line numbers identify the primary code.

| Stage | Evidence and consequence |
| --- | --- |
| Select and inspect a member | `backend/core/src/main/java/org/artifactory/repo/virtual/interceptor/MavenMetadataInterceptor.java:84–89,100–142`: interception tests the metadata path, with no package-type or local/remote condition. `repo.getInfo` is at 119, before the content-read `try`. Unfound members are skipped; blocked members return immediately. The outer per-member catch handles only `RepoRejectException` and `BinaryRejectedException`. |
| Read member content | Same file, **186–208**: `getResourceStreamHandle`, `getInputStream`, full UTF-8 read, and metadata parsing are within catches for **`IOException` and `StorageException`**, followed by a quiet close and `return null`. This applies to local and remote members alike. `base/common/src/main/java/org/artifactory/maven/MavenModelUtils.java:135–141,162–169` also maps invalid XML to `IOException`, so malformed content shares this tolerance. |
| Continue the merge | Interceptor **175–183** merges only non-null metadata. At **145–159**, no merged metadata yields an unfound resource, or a retained authorization result; readable metadata yields a merged `ResolvedResource`. Serialization `IOException` also becomes unfound. `backend/core/src/main/java/org/artifactory/resource/UnfoundRepoResource.java:41–48` defaults unfound to **404**. Thus a caught content fault can yield 404 with no usable member, or a successful partial merge with a usable member, subject to existing priority/authorization rules. This is a source-control-flow conclusion, not a captured wire response. |
| Open local content | `backend/core/src/main/java/org/artifactory/repo/service/RepositoryServiceImpl.java:2931–2954` delegates to the member after permission checks. `backend/core/src/main/java/org/artifactory/repo/db/DbLocalRepo.java:165–167` delegates to its storage mixin. `backend/core/src/main/java/org/artifactory/repo/db/DbStoringRepoMixin.java:894–929` performs another item lookup, throws `FileNotFoundException` if it disappeared, and creates a lazy `file::getStream` handle. Both this second DB lookup and subsequent content read are inside the interceptor's tolerant catch. |
| Read the local binary | `storage/db/src/main/java/org/artifactory/storage/db/fs/model/DbFsFile.java:76–82` calls the binary service. `storage/binaries/bridges/a2b-bridge/src/main/java/org/artifactory/sh/service/ArtifactoryBinaryServiceImpl.java:114–131` and `StorageBinaryServiceImpl.java:293–306` wrap `StorageServiceException` in the caught Artifactory `StorageException`. This directly contradicts a blanket 500 requirement for genuine binary-service failures. The external `BinaryNotFoundException` class hierarchy is absent from this archive; its precise missing-binary behavior was not independently established. |

### Initial item lookup really can abort

`storage/db/src/main/java/org/artifactory/storage/db/fs/service/FileServiceImpl.java:164–167,405–418` converts a failed node SQL lookup into `VfsException`, distinguishing it from a missing node. `storage/db/src/main/java/org/artifactory/storage/db/fs/model/DBImmutableItemProvider.java:116–134,155–168` turns only `VfsItemNotFoundException` into null and rethrows other storage failures. `storage/common/src/main/java/org/artifactory/storage/fs/VfsException.java:30` extends `StorageException`.

`DbLocalRepo.java:153–161` → `DbStoringRepoMixin.java:492–510,833–835` → interceptor line 119 preserves this failure. The outer chain also preserves it: `backend/core/src/main/java/org/artifactory/repo/virtual/VirtualRepo.java:502–513,569–585` catches only `PackageVirtualTraversalException`; `backend/core/src/main/java/org/artifactory/repo/virtual/ArtifactoryVirtualDownloadStrategy.java:84–138,158–174` does not catch it; `backend/core/src/main/java/org/artifactory/engine/DownloadServiceImpl.java:421–461,537–565` does not normalize runtime lookup failures. Finally, **`web/application/src/main/java/org/artifactory/webapp/servlet/RepoFilter.java:528–585` sends 500 for an uncaught non-IO exception before response commitment.** This completes the initial item-statement failure trace; being outside the inner catch alone was insufficient evidence.

### Configuration support is narrower than “every config failure”

`backend/core/src/main/java/org/artifactory/repo/cache/RepoConfigCache.java:576–600,665–693` rethrows known-key cache-loader failures as `IllegalStateException`. Member assembly obtains these configurations before interception (`VirtualRepositoriesResolver.java:104–110`; `VirtualRepositoryConfigResolverImpl.java:123–125`; both under `backend/core/src/main/java/org/artifactory/repo/virtual/`; `backend/core/src/main/java/org/artifactory/repo/service/RepositoryConfigServiceImpl.java:916–936,2240–2251`). Those thrown failures follow the abort/500 route above. Request-scope wrappers preserve supplier exceptions (`RepoConfigCache.java:264–280`; `base/api/src/main/java/org/artifactory/threadlocal/cache/ReposItemsThreadLocalCacheService.java:64–88`).

However, `RepoConfigCache.java:629–651` catches **all exceptions** in an optional cache-miss DB fallback and returns null. Therefore a universal config-fault 500 claim is false for this source. A test for a failed lookup of an existing known member has substantially better support than that universal claim.

## Acceptance assessment

| Proposed assumption | Audit result |
| --- | --- |
| Initial local item statement failure must abort instead of becoming absence/partial success | **Supported by 7.161.26 source and its outer HTTP mapping.** Artifactweave's separate SQLite/PostgreSQL fault injection establishes its own regression, not an Artifactory capture. |
| Known-member configuration loader failure must abort | **Supported for the throwing loader path; qualified by the cache-miss fallback exception above.** Exact modern 7.x configuration failure behavior remains unobserved. |
| Local blob open/read, bridged binary-service failure, or failed member served-copy read must always answer 500 | **Contradicted for `IOException`/`StorageException` during member content acquisition in 7.161.26.** Preserve deliberate tolerance unless newer first-party evidence establishes a change. Do not hide this contradiction behind an inference label. |
| The same interceptor policy covers raw `maven-metadata.xml` under Maven/Generic/npm/NuGet | **Source-supported when the Artifactory download strategy is selected**, because registration includes all interceptor beans (`VirtualRepo.java:220–235`) and interception checks only the path. Exact current cross-package wire results are **unproven**; `VirtualRepo.java:588–595` permits an alternate package-resolution strategy. This does not establish npm/NuGet native metadata API behavior. |
| Missing/denied/malformed members remain passable; streams close | **Supported** by interceptor 119–142,175–208, subject to retained authorization/blocked-resource handling. Its existing tests cover local/remote priority/cache skipping and blocked resources, **not injected storage faults** (`backend/core/src/test/java/org/artifactory/repo/virtual/interceptor/MavenMetadataInterceptorTest.java:83–102,114–212`). |
| Exact checksum-sidecar status, late revalidation/authority fences, sanitized error text, log count, and all newer 7.x behavior | **Not established by this audit.** Existing Artifactweave contracts may govern these separately; they are not evidence that Artifactory's member-content tolerance changed. |

Compatibility qualification should therefore separate initial statement/configuration resolution from tolerant member-content acquisition. A generic typed-own-storage rule does not, by itself, resolve this interceptor-specific contrary evidence.
