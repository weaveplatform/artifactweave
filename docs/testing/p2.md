# Eclipse p2 repository client and qualification

Use `packageType: p2` for remote and virtual repositories. The current
[JFrog p2 guide](https://docs.jfrog.com/artifactory/docs/p2-repositories)
and [package-client class table](https://docs.jfrog.com/artifactory/docs/repository-support-for-package-clients)
list those two classes. There is no native local or federated p2 repository.
To expose an update site stored in artifactweave, deploy its published files
to a local Generic or Maven repository and add that repository to a p2 virtual.

Point the Eclipse installation manager or p2 director at:

```text
https://<host>/artifactory/<p2-repo>/
```

For a remote, set `url` to an upstream update-site directory. The documented
archive form `https://upstream.example/site.zip!/` resolves entries within a
ZIP update site. A virtual serves composite p2 metadata whose child order
matches the configured member order. Each request checks the virtual and
selected member's read permissions. Remote files use the shared source
policy for redirects, cache-only reads, refresh, and offline behavior.
Metadata, JARs and archives are bounded and validated before remote cache
publication. The p2 repository rejects uploads and paths outside native p2
metadata, plugin, feature and binary paths.

## Native client evidence

[`@p2` acceptance](../../test/acceptance/features/p2.feature) runs the
[Eclipse headless p2 director](https://help.eclipse.org/latest/topic/org.eclipse.platform.doc.isv/guide/p2_director.html)
from Eclipse Platform **4.41.0.I20260828-1142**, pinned by the official
archive SHA-512 in the [client image](../../test/acceptance/clients/p2.Dockerfile).
It runs `-list` and `-installIU` against a remote update site, a virtual over
local Generic, and a remote `site.zip!/` update site. The remote case repeats
`-list` through the cache after the upstream stops. Each installed plugin is
checked against its published SHA-256.

The controlled upstream serves unmodified files from the published
[Eclipse GLSP 2.7.0 update site](https://download.eclipse.org/glsp/server/p2/releases/2.7.0/),
retrieved on 2026-10-25. These files are held in

Run the focused proof with:

```sh
ARTIFACTWEAVE_ACCEPT_LOCAL=1 ARTIFACTWEAVE_P2_IMAGE=artifactweave-accept-p2 \
  ARTIFACTWEAVE_ACCEPT_TAGS=@p2 go test -timeout=15m -count=1 -run '^TestFeatures$' ./test/acceptance
```

On a macOS host using Docker Desktop, add `ARTIFACTWEAVE_P2_DESKTOP=1`.
The scenario uses a locally trusted HTTPS test certificate because Eclipse
4.41 requires HTTPS for p2 remote URLs. The acceptance front supplies the
test principal's Basic credentials; server tests separately verify denied
read paths, malformed metadata, archive traversal, and cache admission.

The controlled tests establish protocol behavior against the pinned Eclipse
client, not a live Artifactory target build. The target-version comparison
remains [#216](https://github.com/weaveplatform/artifactweave/issues/216).
Composite sites with external child URLs, Pack200 artifacts, and P2 custom
transport variants are not covered by this acceptance fixture.
