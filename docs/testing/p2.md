# Eclipse p2 repository client and qualification

Use `packageType: p2` for remote and virtual repositories. The current
[JFrog p2 guide](https://docs.jfrog.com/artifactory/docs/p2-repositories)
and [package-client class table](https://docs.jfrog.com/artifactory/docs/repository-support-for-package-clients)
list those two classes. There is no native local or federated p2 repository.
To expose an update site stored in artifactweave, deploy its published files
to a local Generic or Maven repository and add that repository to a p2 virtual.

Point the Eclipse installation manager or p2 director at:

```text
https://<host>/artifactory/<p2-repo>/
```

For a remote, set `url` to an upstream update-site directory. The documented
archive form `https://upstream.example/site.zip!/` resolves entries within a
ZIP update site. A virtual serves composite p2 metadata whose child order
matches the configured member order. Each child is a member's key, and a
client reads the member's files at `/artifactory/<p2-virtual>/<member key>/<path>`,
the form of JFrog's own p2 virtual requests such as
`p2-virtual/download.eclipse.org/releases/luna/p2.index`, where
`download.eclipse.org` is the key of the remote repository JFrog created for
that host ([RTFACT-7631](https://jfrog.atlassian.net/browse/RTFACT-7631),
[RTFACT-29198](https://jfrog.atlassian.net/browse/RTFACT-29198)). A member's
path is the same for every caller and does not change when another member is
blacked out or not readable, and the virtual's include and exclude patterns
match it, member key included. Each request checks the virtual and selected
member's read permissions. Remote files use the shared source
policy for redirects, cache-only reads, refresh, and offline behavior.

A virtual's update sites are listed in `p2Urls` (`p2.urls` in YAML), each an
http or https URL or `local://<key>[/<suffix>]` for a local member and its path
suffix ([RTFACT-29915](https://jfrog.atlassian.net/browse/RTFACT-29915)). The
composite then lists one child per site: for a URL, the first member remote
whose `url` starts it, at `<remote key>/<rest of the URL>`; for a local entry,
`<key>[/<suffix>]`. So with a remote `download.eclipse.org` over
`https://download.eclipse.org/`, the sites
`https://download.eclipse.org/releases/luna` and `.../juno` are the children
`download.eclipse.org/releases/luna` and `download.eclipse.org/releases/juno`.
A member no site names is left out of the composite but stays readable under
its key. Without `p2Urls` the composite lists each member at its root, so set
a member remote's `url` to the update site itself.

Creating a p2 virtual through the repositories API, or updating one with a
request that sends `p2Urls`, adds what each site needs to `repositories`, as
Artifactory's UI does when it saves one
([RTFACT-30256](https://jfrog.atlassian.net/browse/RTFACT-30256)): the P2
remote that already covers the URL, or a new P2 remote keyed by the URL's
host (`<host>-<port>` when it names a port, then `-1`, `-2` while the key is
taken) whose `url` is the host's root; and the local repository a `local://`
entry names, which must be a local Generic or Maven repository. Members are
only added, never removed, and an entry that is not one of the two forms
answers 400 with nothing stored. A YAML apply or a configuration patch
stores `p2Urls` as given and creates nothing; the composite then skips a site
no member serves.
Metadata, JARs and archives are bounded and validated before remote cache
publication. The p2 repository rejects uploads and paths outside native p2
metadata, plugin, feature and binary paths.

An upstream composite can name an absolute child URL. The remote repository
admits its own origin by default; an administrator must list each other origin
in `p2ChildOrigins`. This option is valid only on a remote P2 repository:

```json
{
  "rclass": "remote",
  "packageType": "p2",
  "url": "https://updates.example.org/parent/",
  "p2ChildOrigins": ["https://bundles.example.org"]
}
```

The repository rewrites every admitted child location to an opaque path under
its own `/artifactory/<repo>/` URL. On each child request it checks the parent
composite through the source cache, verifies the child remains named by that
parent, and applies current read permissions. It fetches child metadata and
bundles through the P9 source policy and cache. A child bundle is pinned to the
SHA-256 or SHA-512 declared in its artifact metadata when present. Redirects stay on the selected
child origin. Repository credentials, cookies and client certificates are not
forwarded to another origin, including when `allowAnyHostAuth` is configured.
A P2 virtual retains its configured member order and member-specific origin
policy. Child paths cannot be forged into an arbitrary outbound fetch.

Composite expansion is bounded to five child hops, 64 children per metadata
file, 2,048 bytes per child URL, 36 MiB of expanded metadata and 512 MiB of
archive data. Cycles, path traversal, malformed XML and disallowed origins
fail without returning the upstream child location to the client. A remote
cache URL (`<repo>-cache`) never falls back to the origin on a miss.

A P2 file's GET, a virtual repository's `p2.index` and composite metadata and
the member files it serves under each member's key, takes the query
parameters Artifactory documents for any file, such as `skipUpdateStats`, and
matrix parameters, matched against the file's properties, once the caller's
read permission is settled (#1350). The virtual repository's own files carry no
properties, so only a mandatory key (`;key+=value`) refuses them. A remote
passes the matrix parameters to its upstream after the path, and the query
only when its Propagate Query Params is set. An external composite child and
an update-site archive's entry are fetched from another URL, so their
parameters are matched against a cached copy and not passed on.

## Anonymous access and Force Authentication

With anonymous access on, an anonymous Eclipse client gets what the anonymous
user may read, and a virtual's composite lists only the members it may read.
The client sends credentials only after a 401, so it never asks for the rest
([RTFACT-29198](https://jfrog.atlassian.net/browse/RTFACT-29198)). Set
`forceP2Authentication: true` on the p2 virtual, the **Force Authentication**
checkbox of JFrog's
[Allow Anonymous Access for P2](https://docs.jfrog.com/artifactory/docs/p2-repositories#allow-anonymous-access-for-p2),
and every request without credentials to `/artifactory/<p2-virtual>/...`
answers 401 with `WWW-Authenticate: Basic realm="Artifactory Realm"` and
`{"errors":[{"status":401,"message":"Unauthorized"}]}` before any member is
listed or read, whatever the anonymous user may read. That covers `p2.index`,
the composites, folders and every `<member key>/` path, for every method and
query, `?trace`, `PUT` and `DELETE` included, whether anonymous access is on or
off. The status, challenge and message are those of 7.x's force-authentication
filter (`OssForceAuthenticationFilter`, 7.161.26), which runs in the
authentication chain before the request reaches the repository; artifactweave
applies it in the same place, ahead of routing, for Maven virtual repositories
with `forceMavenAuthentication` too
([#1435](https://github.com/weaveplatform/artifactweave/issues/1435)).
While anonymous access is on, the anonymous user's Basic credentials, Basic
credentials with a blank user name, and a Bearer token that does not verify or
whose subject is anonymous count as none there, as in the filter
(`checkIfAuthenticationShouldBeIgnored`). Signed-in callers, callers whose
credentials name another user, verified or not, and every caller while the flag
is off, get the same answers as before. So do the credentials the filter passes
on to authentication: `Basic Og==` and a lowercase `basic`, which it does not
class as Basic, and an empty `Authorization` or an `X-Api-Key` header, which it
counts as present; authentication answers an empty header, `Basic Og==` and a
lowercase `basic` as it answers no credentials
([#1451](https://github.com/weaveplatform/artifactweave/issues/1451)).

Only the flag of the virtual the request names counts, as 7.x's filter reads
the key from the request's path. A nested p2 virtual read through an outer
virtual uses the outer virtual's flag, and its own is not checked **[I]**,
which waits for the comparison with live 7.x in
[#216](https://github.com/weaveplatform/artifactweave/issues/216). A remote
stores the flag but it changes no answer: JFrog lists Force Authentication
among the
[p2 virtual settings](https://docs.jfrog.com/artifactory/docs/virtual-repositories#additional-settings-for-p2-virtual-repositories)
and not among the
[p2 remote settings](https://docs.jfrog.com/artifactory/docs/remote-repositories#additional-settings-for-p2-remote-repositories),
and 7.x's filter reads it from a virtual alone. Point Eclipse at a p2 virtual
to have it asked for credentials.

## Native client evidence

[`@p2` acceptance](../../test/acceptance/features/p2.feature) runs the
[Eclipse headless p2 director](https://help.eclipse.org/latest/topic/org.eclipse.platform.doc.isv/guide/p2_director.html)
from the [current pinned Eclipse Platform](ci-client-images.md), with its complete
release path and official archive SHA-512 in the [client image](../../test/acceptance/clients/p2.Dockerfile).
It runs `-list` and `-installIU` against a remote update site, a virtual over
local Generic, a remote `site.zip!/` update site, an external child of a
composite remote, and an ordered virtual containing that remote and a local
Generic member. The external-child case clears the Eclipse client state and
repeats both list and install through the repository cache after both
upstreams stop. A negative scenario serves a structurally valid JAR with a
checksum different from the published artifact metadata and verifies that
install fails. Each installed plugin is checked against its published SHA-256.

The controlled upstream serves unmodified files from the published
[Eclipse GLSP 2.7.0 update site](https://download.eclipse.org/glsp/server/p2/releases/2.7.0/),
retrieved on 2026-10-25. These files are held in
[`testdata`](../../internal/artifacts/ecosystem/p2/testdata):

The external-child scenario generates only the small parent composite, so its
absolute location can refer to the scenario's separate ephemeral origin. The
child `p2.index`, content and artifact metadata, and plugin bytes remain the
published Eclipse files below. The test verifies that the child origin sees
registry fetches and that the Eclipse director receives repository-owned
child paths.

Run the focused proof with:

```sh
ARTIFACTWEAVE_ACCEPT_LOCAL=1 ARTIFACTWEAVE_P2_IMAGE=artifactweave-accept-p2 \
  ARTIFACTWEAVE_ACCEPT_TAGS=@p2 go test -timeout=15m -count=1 -run '^TestFeatures$' ./test/acceptance
```

On a macOS host using Docker Desktop, add `ARTIFACTWEAVE_P2_DESKTOP=1`.
The scenario uses a locally trusted HTTPS test certificate because Eclipse
4.41 requires HTTPS for p2 remote URLs. The acceptance front supplies the
test principal's Basic credentials; server tests separately verify denied
read paths, malformed metadata, archive traversal, and cache admission.

The controlled tests establish protocol behavior against the pinned Eclipse
client, not a live Artifactory target build. The target-version comparison
remains [#216](https://github.com/weaveplatform/artifactweave/issues/216).
Pack200 artifacts and custom P2 transport variants are not part of this
acceptance fixture.
